# 10 · 源码阅读地图与实验手册

> 本章是「工具箱 + 手册」：当你想知道**某段代码在哪里**、**某个现象对应哪个函数**、
> **该做哪个实验来验证猜想**时，来这里查。
>
> 阅读内核网络代码最大的困难不是难，而是**代码太多、入口太多、调用链太深**。
> 破解办法只有两个：**有一张地图**，以及**有一个能验证猜想的实验**。

**定位**：全书索引章。前置：任意章节；建议在读完 [docs/01](01-Linux网络子系统全景与数据流.md) 后立刻读本章。

## 2. 现象 → 源码 速查表（反向索引）

这是本章最实用的一张表：**从你看到的现象/命令输出，倒推该读哪个函数**。

| 你观察到的现象 | 该看的代码 | 关键函数/文件 |
|---|---|---|
| `ss -lnt` 的 `Send-Q` 大 | accept 队列积压 | `inet_csk_accept`、`tcp_check_req`、`net/ipv4/inet_connection_sock.c` |
| `/proc/net/netstat` 的 `ListenOverflows` 增长 | 全连接队列溢出 | `tcp_v4_syn_recv_sock`、`tcp_child_process` |
| `Recv-Q` 持续非 0 | 应用读得慢，数据留在 `sk_receive_queue` | `tcp_recvmsg_locked`、`net/ipv4/tcp.c` |
| 出现 `TIME_WAIT` 堆积 | 主动关闭路径 | `tcp_timewait_state_process`、`tcp_minisocks.c` |
| 端口耗尽（Cannot assign requested address） | 本地端口分配 | `inet_csk_get_port`、`ip_local_port_range` |
| 重传率高 | 重传定时器 / 丢包 | `tcp_retransmit_timer`（`tcp_timer.c`）、`tcp_rtx_queue` |
| 吞吐上不去，`cwnd` 很小 | 拥塞控制 | `tcp_slow_start()`/`tcp_cong_avoid_ai()`（`net/ipv4/tcp_cong.c`）、`cong_avoid` 回调、`tcp_cubic.c` |
| 大响应慢、`wmem` 高 | 发送缓冲 | `tcp_sendmsg_locked` 的 `sk_stream_wait_memory` |
| 偶发几十毫秒延迟 | Nagle + 延迟 ACK | `tcp_nagle_check`（`tcp_output.c`）、`tcp_send_delayed_ack` |
| 环回测试正常、上线分片异常 | MTU/PMTU | `ip_fragment`、`ip_rt_update_pmtu`、`tcp_mtu_probing` |
| `softnet_stat` 第 2 列增长 | backlog 溢出 | `net_rx_action`、`process_backlog`（`net/core/dev.c`） |
| `softnet_stat` 第 3 列增长 | 软中断时间片耗尽 | `net_rx_action` 的 `time_limit`、`netdev_budget_usecs` |
| 网卡 `rx_missed_errors` 增长 | 驱动 RX ring 溢出 | 驱动 `napi_poll`、`ethtool -G` 的 ring 参数 |
| `skb:kfree_skb` 频繁 | 某处主动丢包 | tracepoint 的 `caller` 字段直接给出函数名 |
| ARP 大量请求 | 邻居解析失败/过期 | `neigh_resolve_output`、`arp_process`（`net/core/neighbour.c`、`arp.c`） |
| conntrack 表满 | 连接跟踪哈希表 | `nf_conntrack_core.c`、`nf_conntrack_max` |
| DNAT 后回包不对 | NAT 与路由重查 | `nf_nat_ipv4_fn`、`ip_route_me_harder` |
| 抓包在协议栈之前拿到数据 | AF_PACKET | `packet_rcv`、`net/packet/af_packet.c` |

## 3. 六条主干调用链（背下来，读代码时当锚点）

```
【1】发送 TCP 数据
write/recvmsg → sock_sendmsg → inet_sendmsg → tcp_sendmsg → tcp_push
  → __tcp_push_pending_frames → tcp_write_xmit → tcp_transmit_skb
  → ip_queue_xmit → __ip_queue_xmit → ip_local_out → __ip_local_out
  → [nf LOCAL_OUT] → dst_output → ip_output → [nf POST_ROUTING]
  → ip_finish_output → ip_finish_output2 → neigh_output
  → __dev_queue_xmit → [qdisc] → dev_hard_start_xmit → ndo_start_xmit

【2】接收并交付到 TCP
硬中断 → napi_schedule → [NET_RX_SOFTIRQ] → net_rx_action → napi_poll
  → napi_gro_receive → netif_receive_skb → __netif_receive_skb_core
  → [ptype_base] → ip_rcv → ip_rcv_core → [nf PRE_ROUTING] → ip_rcv_finish
  → ip_rcv_finish_core（路由判定 + early demux）→ dst_input → ip_local_deliver
  → [nf LOCAL_IN] → ip_local_deliver_finish → tcp_v4_rcv → __inet_lookup
  → tcp_v4_do_rcv → tcp_rcv_established → tcp_data_queue → sk_data_ready
  → ep_poll_callback → epoll_wait 返回 → recvmsg → tcp_recvmsg

【3】三次握手（服务端）
SYN:  tcp_v4_rcv → tcp_v4_do_rcv → tcp_rcv_state_process → tcp_conn_request
        → tcp_v4_send_synack（SYN 队列 request_sock）
ACK:  tcp_v4_rcv → tcp_check_req → tcp_v4_syn_recv_sock → tcp_child_process
        → 进入 accept 队列（icsk_accept_queue）
用户态 accept(): inet_csk_accept

【4】四次挥手
close() → tcp_close → tcp_send_fin → tcp_write_xmit …
对端 FIN: tcp_rcv_state_process → tcp_fin → 状态迁移
TIME_WAIT: inet_csk_complete_hashdance / tcp_timewait_state_process（超时后释放）

【5】转发（路由器行为）
ip_rcv_finish_core（判定非本机）→ ip_forward → [nf FORWARD]
  → ip_forward_finish → dst_output → ip_output → [nf POST_ROUTING] → dev_queue_xmit

【6】丢包（tracepoint 视角）
kfree_skb_reason() ← 所有丢包点统一入口
  常见调用者：tcp_v4_rcv（找不到 socket）、ip_rcv_core（校验和/长度）、
             netif_receive_skb_core、udp_queue_rcv_skb（队列满）、
             __netif_receive_skb_core（无匹配协议）
```

**用法**：读到一个陌生函数时，先在上面六条链里定位它在哪一段，再上下各展开一层，就够用了。

## 4. 读源码的工程手段

### 4.1 交叉引用（最有效的一招）

```
https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/tcp_input.c
  → 点任意标识符，能看到「定义」与「所有引用」
  → 这是理解「谁调用我 / 我调用谁」最快的路径
```

读内核时**不要**从文件头顺序读；用「**从现象/函数名出发，看交叉引用，上下各一层**」的方式读。

### 4.2 本地源码 + 索引

```bash
# 方式 A：只装头文件时（本教程环境的实际情况）
grep -rn "tcp_v4_rcv" /usr/src/linux-headers-$(uname -r)/ | head
# 注意：头文件树只有 include/ 和少量脚本，看不到 .c 实现，所以查实现要靠 elixir。

# 方式 B：有完整源码时（推荐）
tar xf linux-6.12.tar.xz && cd linux-6.12
make defconfig && make prepare          # 生成足够 cscope/clangd 用的信息
cscope -Rbkq -s net -s include -s drivers/net   # 建索引
# 在 vim 里: :cs find c tcp_write_xmit    （找调用者）
#            :cs find d sk_stream_wait_memory（找被调用者）

# 方式 C：clangd（现代体验最好）
bear -- make defconfig prepare           # 生成 compile_commands.json
# 之后在编辑器里跳转/补全/看宏展开
```

### 4.3 用运行时验证猜想（而不是只靠读）

| 手段 | 一行示例 | 适合验证 |
|---|---|---|
| `bpftrace` 打点 | `bpftrace -e 'kprobe:tcp_write_xmit { @=count(); }'` | 函数被调用的频率与栈 |
| tracepoint | `perf trace -e skb:kfree_skb` | 丢包点与原因 |
| `ss -tni` | `ss -tni` | cwnd/rtt/窗口等 TCP 状态 |
| `/proc/net/*` | `cat /proc/net/softnet_stat` | 软中断与队列计数 |
| `ftrace` | `echo 1 > /sys/kernel/tracing/events/tcp/enable` | 事件级跟踪 |
| `printk` | 改源码加 `pr_info` 后重编模块 | 自定义路径（慎用，见 labs/06 安全提示） |

> 本机受限（无 root、无 tracefs、无 bpftrace），所以这些手段在本教程里是**模板 + 前置条件**，
> 见 [labs/09-observability/06-tracepoint-templates.md](../labs/09-observability/)。

### 4.4 读内核代码的五个坑

1. **上下文**：接收路径跑在软中断里，**不能睡眠**。看到 `might_sleep()`/`mutex_lock()` 就要警觉。
2. **per-CPU**：`this_cpu_inc()`、`per_cpu_ptr()` 的数据不是全局的，看到统计数字对不上先想想这点。
3. **RCU**：`rcu_read_lock()` 只是禁止抢占/标记临界区，不等于互斥锁；`rcu_dereference` 读的是快照。
4. **条件编译**：`#ifdef CONFIG_...` 会让你的发行版内核行为与源码默认值不同。用
   `grep CONFIG_ /boot/config-$(uname -r)` 确认实际配置。
5. **静态内联头文件**：大量逻辑在 `include/net/*.h` 的 `static inline` 里
   （`skb_push`、`ip_hdr`、`sk_mem_charge`…），只看 `.c` 会漏掉关键步骤。

## 7. 常见问题

**Q：一定要读完整的内核源码吗？**
不必。网络子系统的核心调用链就那六条（第 3 节）。把六条链上的每一层搞懂，
遇到问题时能定位到函数，就足够覆盖绝大多数工作场景；深入某个具体机制时再展开。

**Q：源码版本不一致怎么办？**
函数名与文件路径在 6.x 内总体稳定，但细节会变（例：IPv4 路由缓存在 4.18 被移除，
改为 FIB trie 直查）。**永远以你机器上的实际版本为准**——所以本教程刻意**不写行号**，
并给出 `elixir.bootlin.com/linux/v6.12/source/` 作为核对入口。

**Q：为什么本教程的实验大量依赖环回（`lo`）？**
两个原因。一是**环回最省事**：它能完整走一遍协议栈（只有真实驱动与 NAPI 被跳过），
对理解数据流已经足够。二是受环境限制：**初始命名空间**里 `CapEff=0`，
不能加载内核模块、不能用 eBPF、缺 `/dev/net/tun`。

但要更正一个常见误解：**netns/veth 并不是完全不可用**。实测
`unshare -Urnmpf --mount-proc` 之后在新用户命名空间内 `CapEff=000001ffffffffff`，
可以建 veth、改 MTU、使用 `AF_PACKET`（所以 [labs/04](../labs/04-raw-socket-arp/)
的 ARP 实验是**真能跑**的）。两个坑：`/sys` 无法重挂（`mount -t sysfs` 返回 EPERM），
所以接口 MTU/统计要用 `ip link show` 与 `/proc/net/dev` 看；`ip netns add` 需要写
只读的 `/run/netns`，改用两个 `unshare -n` 进程 + `nsenter`。
仍然真的做不到的是：加载内核模块、加载 eBPF、TUN 设备（缺设备节点且 userns 内 `mknod` 被拒）。

**Q：怎么知道自己的理解是对的？**
用实验验证。能用 `ss`、`/proc/net`、解析器单测、内核模块统计验证的结论才是可靠的；
「我觉得应该是这样」不算。这也是本教程给每个 lab 都配「观察与思考题」的原因。
