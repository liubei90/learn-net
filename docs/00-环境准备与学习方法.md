# 00 · 环境准备与学习方法

> 本章解决三个问题：**按什么顺序学**、**在哪里学（环境怎么搭）**、
> **遇到不懂的内核代码怎么自己查下去**。
>
> 读完本章你应该能回答：
> 1. 我这台机器现在能做哪些实验，哪些做不了，为什么？
> 2. 我要读某个机制的内核实现，应该从哪个文件、哪个函数下手？
> 3. 一个函数跑在进程上下文还是软中断上下文，我怎么判断？

## 0. 本章定位

这是**全书的第一章**，也是唯一一章"讲方法而不是讲网络"的内容。

Linux 网络子系统体量极大：`net/` 目录下有上万个文件、几十万行代码。
如果没有路线和方法，很容易出现两种失败：

- **在 API 层打转**：会写 `socket()`/`epoll`，但一遇到"为什么丢包""为什么延迟抖动"
  就无从下手，因为不知道内核里发生了什么。
- **掉进函数细节**：打开 `tcp_input.c`（5000+ 行）从第一行读起，读完也不知道主干在哪。

本教程的对策是：**先给一张地图（`docs/01`），再配一套观测手段（`docs/09`），
然后用六条主干调用链把细节挂到地图上（`docs/10`）。**
本章负责把"路线"和"工具"准备好。

### 目标读者

| 你是 | 建议起点 |
|---|---|
| 会写 socket 程序，但不懂内核 | `docs/01` 全景 → `labs/09` 学会观测 → 按 8 周路线走 |
| 有 Linux 运维/排障经验 | `docs/09` 观测与调优 → `docs/05` NAPI/中断 → `docs/06` netfilter |
| 准备内核/基础架构面试 | `docs/10` 速查表 + 六条主干调用链，逐个手推 |
| 想写内核模块或 eBPF | `docs/01` → `docs/07` → `labs/06`、`labs/08` |

缺哪补哪，不必全补完再开始。

但要习惯读英文注释和 LWN 文章）。

### 一个学习心态上的提醒

内核网络代码里**没有"猜"的空间**。本教程反复强调一条纪律：

> 任何关于内核行为的结论，要么有**源码依据**（文件 + 函数名），
> 要么有**实测依据**（命令 + 真实输出）。两者都没有，就应该说"我不确定"。

这也是本教程在"没有 root 的机器上"仍然坚持把能跑的实验**真跑一遍**、
把跑不了的写清前置条件的原因 —— **区分"验证过的"和"听说的"**，
比多记住几个函数名重要得多。

## 2. 实验环境搭建（三档）

按"你需要什么权限"把实验环境分成三档。**大多数人只需要第 1 档**。

### 2.1 第 1 档：任意 Linux 发行版 + 用户态实验

**需要**：任何 Linux（WSL2、容器、云主机、虚拟机都行）+ gcc + python3 + iproute2。
**不需要**：root、内核源码、内核头文件。

这档能覆盖本教程的**大部分**内容：

| 能做 | 对应 lab |
|---|---|
| socket API、缓冲区记账、epoll、`TCP_INFO` | labs/01 |
| TCP 状态机、accept 队列溢出、TIME_WAIT | labs/02 |
| rtnetlink dump（读链路/地址/路由） | labs/03 |
| HTTP/1.1 增量解析器 | labs/07 |
| **`ss` / `/proc/net` / sock_diag / 丢包计数器观测** | labs/09 |

```bash
# 确认你在第 1 档
uname -r            # 有输出即可
gcc --version       # 需要
python3 --version   # 需要
ip -j link show     # 需要非特权可用
cat /proc/net/softnet_stat   # 需要可读
```

### 2.2 第 2 档：需要 root 的实验

**需要**：root（或 `CAP_NET_ADMIN`），用于建网络命名空间、veth、改 sysctl、
抓包、加载内核模块。

典型用途是**在一台机器上搭出多台"虚拟主机"的拓扑**，用来验证转发、NAT、路由。

#### 完整命令序列：两个命名空间 + 一条 veth 对

```bash
# 0) 确认你的内核支持网络命名空间
ls /proc/self/ns/net            # 存在即可
unshare --net true && echo "netns OK"

# 1) 建两个网络命名空间
ip netns add ns1
ip netns add ns2

# 2) 建一对 veth（虚拟网线，成对出现，一端进一个命名空间）
ip link add veth1 type veth peer name veth2

# 3) 把两端分别塞进两个命名空间
ip link set veth1 netns ns1
ip link set veth2 netns ns2

# 4) 配 IP 地址
ip netns exec ns1 ip addr add 10.0.0.1/24 dev veth1
ip netns exec ns2 ip addr add 10.0.0.2/24 dev veth2

# 5) 把接口和 lo 都拉起来（lo 不拉起来，本机回环服务会不通）
ip netns exec ns1 ip link set lo up
ip netns exec ns2 ip link set lo up
ip netns exec ns1 ip link set veth1 up
ip netns exec ns2 ip link set veth2 up

# 6) 验证连通性
ip netns exec ns1 ping -c 2 10.0.0.2

# 7) 在命名空间里做观测（这就是「一台虚拟主机」）
ip netns exec ns1 ss -lntup
ip netns exec ns1 cat /proc/net/dev
ip netns exec ns1 cat /proc/net/softnet_stat
ip netns exec ns1 nstat -az 2>/dev/null | head    # 若装了 iproute2 的 nstat

# 8) 清理（veth 是成对的，删一端另一端自动消失）
ip netns del ns1
ip netns del ns2
```

**加一个"路由器"命名空间（验证 IP 转发）**：

```bash
ip netns add r1
# r1 与 ns1 之间
ip link add vr1 type veth peer name vr2
ip link set vr1 netns r1
ip link set vr2 netns ns1
# r1 与 ns2 之间
ip link add vr3 type veth peer name vr4
ip link set vr3 netns r1
ip link set vr4 netns ns2

ip netns exec r1 ip addr add 10.0.0.254/24 dev vr1
ip netns exec ns1 ip addr add 10.0.0.1/24 dev vr2
ip netns exec r1 ip addr add 10.1.0.254/24 dev vr3
ip netns exec ns2 ip addr add 10.1.0.1/24 dev vr4

for i in r1 ns1 ns2; do
    ip netns exec $i ip link set lo up
done
ip netns exec r1 ip link set vr1 up
ip netns exec r1 ip link set vr3 up
ip netns exec ns1 ip link set vr2 up
ip netns exec ns2 ip link set vr4 up

# 打开转发（注意：这是在 r1 命名空间里改，不影响宿主机）
ip netns exec r1 sysctl -w net.ipv4.ip_forward=1
# 若无 sysctl 命令，用： ip netns exec r1 sh -c 'echo 1 > /proc/sys/net/ipv4/ip_forward'

# 给两端加路由，指向 r1
ip netns exec ns1 ip route add 10.1.0.0/24 via 10.0.0.254
ip netns exec ns2 ip route add 10.0.0.0/24 via 10.1.0.254

# 验证跨网段连通
ip netns exec ns1 ping -c 2 10.1.0.1

# 顺便看 ARP 与路由表
ip netns exec ns1 ip neigh show
ip netns exec ns1 ip route show
```

**这套拓扑能验证什么**（都是"读文档永远记不牢"的东西）：

- veth 的**成对统计**：`ip netns exec ns1 cat /proc/net/dev` 看 `veth1` 的 TX，
  对应 ns2 侧 `veth2` 的 RX —— 一端发、一端收，数字应当对得上。
- **转发发生在内核的哪一步**：`ip_forward=1` 打开前后，`ping` 的结果差异。
- **TTL 递减与 ICMP 超时**：`ping -t 1` 打到远端，验证 `ip_decrease_ttl`。
- **conntrack 表**（若装了 `conntrack`）：做一次 DNAT 看表项怎么建。

#### 清理纪律

命名空间和 veth 都是**引用计数**的。忘了删会一直占着资源，
`ip netns list` 和 `ip link show type veth` 能看到残留：

```bash
ip netns list
ip -d link show type veth
# 批量清理
for n in $(ip netns list | awk '{print $1}'); do ip netns del "$n"; done
```

### 2.3 第 3 档：完整内核实验

**需要**：root + 一台可以随便折腾的机器（虚拟机/云主机）。
涉及编译内核、跑虚拟机、用 ftrace/kgdb 调试。

> ⚠️ **不要在唯一的生产机上做这一档的实验。**

#### (a) 编译内核并启用调试信息

```bash
# 1) 装依赖（Debian/Ubuntu）
sudo apt-get install -y build-essential libncurses-dev bison flex \
    libssl-dev libelf-dev bc dwarves zstd git

# 2) 取源码（选一种）
git clone --depth 1 -b v6.12 \
    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git linux-6.12
# 或
apt-get source linux-image-$(uname -r) 2>/dev/null

cd linux-6.12

# 3) 用当前系统配置作为起点，避免从零配
cp /boot/config-$(uname -r) .config
make olddefconfig

# 4) 打开调试相关选项（make menuconfig 或直接改 .config）
#    Kernel hacking →
#      CONFIG_DEBUG_INFO=y                # 调试符号（gdb/objdump 需要）
#      CONFIG_DEBUG_INFO_DWARF5=y
#      CONFIG_FRAME_POINTER=y             # 可靠的调用栈
#      CONFIG_FTRACE=y                    # ftrace
#      CONFIG_FUNCTION_TRACER=y
#      CONFIG_FUNCTION_GRAPH_TRACER=y
#      CONFIG_KPROBES=y
#      CONFIG_KPROBE_EVENTS=y
#      CONFIG_DEBUG_INFO_BTF=y            # BTF，bpftrace/bpftool 依赖
#      CONFIG_GDB_SCRIPTS=y               # 提供 gdb 辅助脚本
#      CONFIG_KGDB=y
#      CONFIG_KGDB_SERIAL_CONSOLE=y
#    以及 Debug filesystem → CONFIG_DEBUG_FS=y

# 5) 编译（-j 用「CPU 核数」或「核数+1」）
make -j"$(nproc)"           # 首次编译通常 20–60 分钟
sudo make modules_install
sudo make install           # 装 vmlinuz + initramfs
sudo update-grub            # Debian/Ubuntu
# sudo grubby --update-kernel=ALL --args="..."   # RHEL 系
```

> 编译内核是"体力活"，本教程**不要求**你做。但它是拿到 `vmlinux`
> （带符号的内核镜像）与 `compile_commands.json` 的唯一可靠途径，
> 对 `docs/00` 第 4 节的源码阅读帮助极大。

#### (b) 在虚拟机里跑你的内核

**方案 1：QEMU + 磁盘镜像**（最可控，调试能力最强）

```bash
# 用 cloud image 做 rootfs
curl -O https://cloud.debian.org/images/cloud/trixie/latest/debian-13-genericcloud-amd64.qcow2
qemu-img resize debian-13-genericcloud-amd64.qcow2 +20G

# 启动：指定自己编译的 bzImage 与 rootfs
qemu-system-x86_64 \
    -m 2048 -smp 2 \
    -kernel arch/x86/boot/bzImage \
    -append "root=/dev/sda1 console=ttyS0" \
    -drive file=debian-13-genericcloud-amd64.qcow2,format=qcow2 \
    -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
    -nographic

# 更省事的做法：用 virtme-ng，直接在当前目录里跑新内核（无需整盘镜像）
#   pip install virtme-ng
#   vng --run .            # 用当前目录编译出的内核启动一个轻量 VM
```

**方案 2：systemd-nspawn**（容器式，最轻量，适合验证用户态与部分网络行为）

```bash
sudo apt-get install -y systemd-container debootstrap

# 建一个最小 Debian rootfs
sudo debootstrap --include=iproute2,iputils-ping,tcpdump trixie /var/lib/machines/netlab

sudo systemd-nspawn -D /var/lib/machines/netlab --boot
# 或者只在容器里跑一条命令
sudo systemd-nspawn -D /var/lib/machines/netlab --network-veth ip ping -c2 10.0.0.1
```

> `--network-veth` 会**自动**创建一对 veth 并在容器里配好地址，
> 比自己敲 `ip link add veth` 省事，很适合快速验证。
> 注意：nspawn 共享宿主内核，所以**不能**用它测试"自己编译的内核"。

**方案 3：buildroot**（最小化，适合测试驱动/协议栈改动）
`make qemu_x86_64_defconfig && make` 直接产出一个可启动镜像。

#### (c) 内核调试与追踪

| 手段 | 用途 | 关键步骤 |
|---|---|---|
| **ftrace function_graph** | 看函数调用链与耗时 | `cd /sys/kernel/tracing; echo function_graph > current_tracer; echo 'tcp_v4_rcv' > set_graph_function; echo 1 > tracing_on; cat trace` |
| **ftrace 事件** | 看 tracepoint 事件流 | `echo 1 > events/tcp/tcp_retransmit_skb/enable; cat trace_pipe` |
| **perf** | 采样 + tracepoint 统计 | `perf record -a -g -- sleep 5; perf report` |
| **bpftrace** | 聚合统计、直方图 | `bpftrace -e 'tracepoint:tcp:tcp_retransmit_skb { @[args->dport]=count(); }'` |
| **kgdb / kgdboc** | 源码级断点调试 | 内核加 `CONFIG_KGDB`，启动参数 `kgdboc=ttyS0,115200 kgdbwait`，宿主机 `gdb vmlinux` 后 `target remote /dev/ttyS0` |
| **QEMU + gdb** | 最推荐的源码级调试 | QEMU 加 `-s -S`，宿主机 `gdb vmlinux -ex 'target remote :1234' -ex 'b tcp_v4_rcv'` |
| **printk / trace_printk** | 最简单的"验证猜想" | `pr_info("sk=%p state=%d\n", sk, sk->sk_state);` 然后 `dmesg -w`。**注意**：`trace_printk` 不能用于生产；`printk` 在高频路径上会拖垮系统 |

> **调试内核网络代码的顺序建议**：先用 **ftrace 事件/tracepoint** 看"发生了什么"，
> 再用 **function_graph** 看"走了哪些函数"，最后才上 **kgdb/gdb** 看"某个变量为什么是那个值"。
> 一上来就断点，很容易在软中断里把系统停死。

### 2.4 ⚠️ 本教程开发机的实际情况：第 1 档，且只能做观测

本教程的编写与验证环境是一台**完全非特权**的机器。实测结果
（由 [`scripts/env-check.sh`](../scripts/env-check.sh) 输出，完整输出见第 3 节）：

```
===== 2. Capabilities 与特权能力 =====
  CapEff (raw)                       0x0000000000000000  =  0
  ❌ CAP_NET_ADMIN (bit 12) 缺失 —— 初始命名空间内无法改 sysctl、配 qdisc/nftables
     （netns/veth 仍可用 unshare -U 在用户命名空间内创建，见第 3 节）
  ❌ CAP_NET_RAW (bit 13) 缺失 —— 无法创建 AF_PACKET 原始套接字（抓包、ping）
  ❌ CAP_SYS_ADMIN (bit 21) 缺失 —— 无法挂载 tracefs、执行大量管理操作
  ❌ CAP_PERFMON (bit 38) 缺失 —— 无法调用 perf_event_open（perf/bpftrace 追踪）
  ❌ CAP_BPF (bit 39) 缺失 —— 无法加载 BPF 程序（bpftrace/bcc）

===== 3. 网络相关内核接口可用性 =====
  ❌ /dev/net/tun 不存在 —— labs/05 的 TUN/TAP 实验无法在本机运行
  ⚠️  unshare --net 直接失败（初始命名空间无 CAP_SYS_ADMIN）——这不代表 netns 实验做不了，
     请看下面第 ② 项：通过用户命名空间可以拿到能力。
  ✅ unshare -Urnmpf --mount-proc 可用 —— 可在用户命名空间内建 netns/veth/改 MTU/AF_PACKET
  ✅ NETLINK_ROUTE 非特权查询可用（ip -j link show 正常）
  ✅ /proc/net/* 全部可读（16/16 个关键文件）—— 观测类实验基础完备
  ✅ /proc/sys/net/* 可读（只读）—— 可以读参数快照
  ✅ NETLINK_SOCK_DIAG 非特权可用（labs/09 的 05-socket-diag.py 可以跑）
```

**结论：第 1 档完全可用，第 2 档打折扣但没被堵死，第 3 档做不到**。原因是：

- `CapEff = 0` → **初始命名空间**内没有任何 capability，`unshare --net` 直接返回 `EPERM`。
  **但** `unshare -Urnmpf --mount-proc` 仍然可用：用户命名空间会让你在内部拿到
  `CapEff=000001ffffffffff`，于是建 veth、改 MTU、用 `AF_PACKET` 都可以（实测）。
  两个限制：`/sys` 无法重挂（EPERM，接口信息要用 `ip`/`/proc/net` 读）；
  `ip netns add` 需要写只读的 `/run/netns`，改用两个 `unshare -n` 进程 + `nsenter`。
  可直接跑 [`scripts/netns-veth-demo.sh`](../scripts/netns-veth-demo.sh) 验证；
- `/dev/net/tun` 不存在 → 用户态协议栈实验（labs/05）无法运行；
- `/sys/kernel/debug` 与 `/sys/kernel/tracing` 虽然**已挂载**（`tracefs` / `debugfs`）
  但挂载选项是 **`ro`（只读）**，且当前用户无读权限 → ftrace 用不了；
- `kernel.unprivileged_bpf_disabled = 2` → 值 **2** 意味着"非特权 BPF 已禁用
  **且无法在运行时重新启用**"（值 1 可以改回 0，2 不行，只能改内核启动参数）；
- 未安装 `perf`/`bpftrace`/`bcc`/`bpftool`/`clang`/`tcpdump`/`strace`。

#### 在这种受限环境下，你依然能做很多事

这是本教程设计上的一个核心判断：**"没有 root"不等于"不能观测内核"。**
内核把大量内部状态通过**只读接口**暴露出来，而这些接口对非特权用户开放：

| 可用的手段 | 原理 | 本教程在哪用 |
|---|---|---|
| `/proc/net/*`（dev/snmp/netstat/sockstat/tcp/softnet_stat/...） | 内核的 seq_file 接口，只读 | labs/09 的 01–04、07 |
| `/proc/sys/net/*` | sysctl 的只读视图 | labs/09 的参数快照 |
| `NETLINK_ROUTE` **查询** | 读链路/地址/路由不需要特权 | `ip -j link show`、labs/03 |
| `NETLINK_SOCK_DIAG` **查询** | `ss` 的底层协议，dump 自己的 netns 无需特权 | labs/09 的 `05-socket-diag.py` |
| `/sys/class/net/*/statistics/*` | 网卡统计，只读 | labs/09 的 03 |
| 编译内核模块 | 本机**有**内核头文件与 `/lib/modules/$(uname -r)/build` | labs/06（能编译，不能 `insmod`） |

所以本机可以完成：**用户态 socket 实验（01、02、07）、netlink 查询（03）、
全部观测类实验（09）**；不能完成：**原始套接字（04，需 `CAP_NET_RAW`）、
TUN/TAP（05）、加载内核模块（06）、eBPF/XDP（08）**。

`env-check.sh` 会打印一张结论表把你的机器归类，本机的实测结论是：

```
===== 8. 结论：本教程 labs 01~09 在本机的可运行性 =====
  ✅  lab/01  socket API 基础 (C 语言)
  ✅  lab/02  TCP 状态机实验
  ✅  lab/03  NETLINK_ROUTE / rtnetlink
  ⚠️  lab/04  原始套接字与 ARP
            需要 CAP_NET_RAW 才能创建 AF_PACKET 套接字；本机缺失
  ⚠️  lab/05  TUN/TAP 用户态协议栈
            需要 root + /dev/net/tun；本机 /dev/net/tun 不存在
  ⚠️  lab/06  内核模块与 netfilter
            本机有头文件**可编译**模块，但非特权无法 insmod 加载
  ✅  lab/07  HTTP 解析器
  ⚠️  lab/08  eBPF / XDP
            需要 CAP_BPF + clang + libbpf + 可写 tracefs；本机全部缺失
  ✅  lab/09  内核网络观测与调优
            已针对本机权限设计：labs/09 的 01~05、07 全部真跑通过
```

**本教程的写作纪律由此而来**：

> 能跑的 **一律真跑**，并把真实输出贴进文档和 lab 的 README；
> 跑不了的 **写成"模板 + 前置条件 + 本机不可运行的确切原因"**，
> 并且脚本自身要能**优雅降级**（检测不到前置条件就打印 `SKIP` 并 `exit 0`）。

这样读者不会拿到一份"看起来能跑其实跑不了"的代码，
也不会因为环境差异而卡住。

> 📌 **一个容易误判的环境陷阱**：在本机直接敲 `sysctl` 会得到
> `bash: sysctl: 未找到命令`，很容易让人以为「机器没装 sysctl」。
> **但这是错的**：`procps` 2:4.0.4 确实提供了 `/usr/sbin/sysctl`（可用 `dpkg -S` 核实），
> 只是 `/usr/sbin`、`/sbin` 不在当前**非登录 shell** 的 `PATH` 里：
>
> ```bash
> $ sysctl -n net.core.somaxconn
> bash: sysctl: 未找到命令          # ← 只是 PATH 问题
> $ /usr/sbin/sysctl -n net.core.somaxconn
> 4096                              # ← 命令本身完全可用
> ```
>
> 即便如此，本教程仍然一律用 `cat /proc/sys/...`：因为它**不依赖 PATH、不依赖工具包、
> 不需要 root**，在任何受限环境下都稳。两者读的是同一份数据：
>
> ```bash
> sysctl -n net.core.somaxconn          # 需要 procps + PATH 正确
> cat /proc/sys/net/core/somaxconn      # 总是可用
> ```
>
> **这个例子本身就是一堂课**：「命令找不到」≠「功能不存在」，
> 诊断环境时要用绝对路径或 `dpkg -S` 求证，不要靠直觉下结论。
> 同类的坑还有 `modprobe`/`modinfo`/`lsmod`（都在 `/sbin`，指向 `/bin/kmod`）。

### 3.2 内核头文件的"意外之喜"

本机虽然不能加载模块，但 `/lib/modules/$(uname -r)/build` 与
`/usr/src/linux-headers-*-common/include/uapi` **都存在**。这带来两个好处：

1. **可以真编译内核模块**（labs/06），只是不能 `insmod`；
2. **可以查权威的 uapi 结构体定义** —— 这在读 netlink 代码时价值极大。
   例如核对我们用到的 `struct inet_diag_msg`：

   ```bash
   grep -n -A 16 'struct inet_diag_msg {' \
       /usr/src/linux-headers-*-common/include/uapi/linux/inet_diag.h
   ```

   因为这份头文件**与运行内核完全同版本**，它比任何在线文档都可靠 ——
   在线文档可能与你的内核不一致，而这份不会。

   同理，tracepoint 的字段定义在
   `/usr/src/linux-headers-*-common/include/trace/events/*.h`。

## 4. 怎么读内核网络源码

这是本章最有"复利"的一节。**会读源码，比记住结论重要**，
因为内核每个版本都在变，而检索方法不变。

### 4.1 不要试图"读完"

`net/` 目录下代码量巨大。正确的姿势是**带着问题读**：

> "`connect()` 之后，内核在哪里把 socket 状态改成 `TCP_SYN_SENT`？"

然后从**已知的锚点**出发，一层层倒推。永远不要从文件第一行开始读。

### 4.2 在线交叉引用：elixir.bootlin.com

本教程统一以 **Linux 6.12** 为基准，对应的检索入口是：

```
https://elixir.bootlin.com/linux/v6.12/source/
```

常用姿势：

| 想做什么 | 怎么做 |
|---|---|
| 看某个文件 | 直接拼路径：`.../source/net/ipv4/tcp_input.c` |
| **查标识符的定义**（最高频） | 左上角 "Identifier" 搜索框输入 `tcp_set_state`，会列出**所有**引用点 |
| 查结构体 | Identifier 搜 `struct tcp_sock`，会跳到定义并列出成员 |
| 看 Kconfig / Makefile 包含关系 | 文件树里可直接打开 `Kconfig` |
| 确认某个版本的函数是否存在 | **先改版本号再搜索** —— 这是核对"6.12 到底有没有这个函数"的最快方法 |

**⚠️ elixir 的一个使用陷阱**：不同版本的默认分支可能不同。
搜索前一定确认地址栏里是 `v6.12`，否则你查到的可能是别的版本的定义。

### 4.3 本地源码 + 索引工具（推荐，比在线快得多）

```bash

git clone --depth 1 -b v6.12 \
    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git linux-6.12
cd linux-6.12

# 2) 生成 compile_commands.json（clangd 需要，精确跳转/补全的前提）

#   常用： 0 查找符号  1 查定义  2 查被调用  3 查调用者  4 查文本

# 4) ctags（vim/emacs 跳转）
ctags -R --c-kinds=+p --fields=+iaS --extras=+q .

# 5) vim 配置片段（~/.vimrc）
#    set tags=./tags,tags
#    cs add cscope.out
#    " 快捷键：Ctrl-] 跳定义，Ctrl-t 返回
#    nmap <C-\>s :cs find s <C-R>=expand("<cword>")<CR><CR>   " 查找符号
#    nmap <C-\>g :cs find g <C-R>=expand("<cword>")<CR><CR>   " 查定义
#    nmap <C-\>c :cs find c <C-R>=expand("<cword>")<CR><CR>   " 查调用者

# 6) VS Code / Neovim + clangd（体验最好）
#    安装 clangd 扩展后，确保 .clangd 或 compile_commands.json 在项目根目录。

#      CompileFlags:
#        Add: [-Wno-everything, -D__KERNEL__]
```

### 4.4 `grep` 查找技巧

```bash
# 找函数定义（内核风格：返回类型与函数名可能跨行，先用宽松模式定位）
grep -rn "^tcp_set_state" net/ --include=*.c
grep -rn "\btcp_set_state\b" net/ --include=*.c --include=*.h

# 找结构体定义
grep -rn -A 20 "^struct tcp_sock {" include/

# 找"谁调用了它"（没有 cscope 时的土办法）
grep -rn "tcp_set_state(" net/ | grep -v "^.*:.*static"

# 找 EXPORT_SYMBOL（判断一个函数是否对模块可见）
grep -rn "EXPORT_SYMBOL.*tcp_" net/ipv4/

# 找 procfs 输出格式（定位 /proc 文件的渲染代码）
grep -rn "softnet_stat" net/
grep -rn "seq_printf" net/core/net-procfs.c

# 找 sysctl 表项（参数名 -> 处理函数）
grep -rn "somaxconn" net/ include/
grep -rn "sysctl_tcp_" net/ipv4/sysctl_net_ipv4.c

# 找 tracepoint 的调用点
grep -rn "trace_tcp_retransmit_skb\|trace_inet_sock_set_state" net/

# 只在 C 文件里搜、排除文档
grep -rn "tcp_rcv_established" --include=*.c net/
```

**几个高频锚点**（记住这些，能省很多时间）：

| 我想找 | 锚点 |
|---|---|
| 系统调用入口 | `net/socket.c`（`__sys_socket`、`__sys_connect`）、`include/linux/syscalls.h` |
| socket 创建 | `net/socket.c:sock_create`、`net/ipv4/af_inet.c:inet_create` |
| TCP 发包 | `net/ipv4/tcp_output.c:tcp_sendmsg` → `tcp_write_xmit` → `__tcp_transmit_skb` → `ip_queue_xmit` |
| TCP 收包 | `net/ipv4/tcp_ipv4.c:tcp_v4_rcv` → `tcp_rcv_established` / `tcp_rcv_state_process` |
| IP 收包 | `net/ipv4/ip_input.c:ip_rcv` → `ip_rcv_finish` → `ip_local_deliver` |
| 路由查找 | `net/ipv4/route.c:ip_route_input_noref`、`fib_lookup`（`net/ipv4/fib_trie.c`） |
| 邻居/ARP | `net/core/neighbour.c`、`net/ipv4/arp.c:arp_process` |
| 软中断收包 | `net/core/dev.c:net_rx_action` → `napi_poll` → `netif_receive_skb` |
| netfilter | `net/netfilter/core.c:nf_hook_slow`、`include/linux/netfilter.h`（5 个 hook 枚举） |
| procfs 输出 | `net/core/net-procfs.c`、`net/ipv4/proc.c`、`net/ipv4/tcp_ipv4.c`（`*_seq_show`） |
| sysctl 定义 | `net/ipv4/sysctl_net_ipv4.c`、`net/core/sysctl_net_core.c` |

### 4.5 从"已知函数名"倒推调用链

这是读源码最核心的技能。示例：**`/proc/net/softnet_stat` 的每一列是从哪来的？**

```
观察到的现象：/proc/net/softnet_stat 每行 15 列，都是 8 位十六进制
   ↓ 猜：这是一个 seq_file，格式化函数名可能含 "softnet"
步骤 1  grep -rn "softnet_stat" net/                      → net/core/net-procfs.c
步骤 2  读该文件，找到 softnet_seq_show()                  → 看到一条 seq_printf
步骤 3  数格式串里有几个 %08x，对照参数列表                  → 确定列序
步骤 4  参数的来源 sd->processed / sd->dropped / ... 
   ↓ 于是要找 struct softnet_data 的定义
步骤 5  grep -rn "struct softnet_data {" include/          → include/linux/netdevice.h
步骤 6  看每个字段的注释，找到写入它的地方
        grep -rn "sd->dropped++\|->dropped++" net/core/dev.c → enqueue_to_backlog()
```

**这条链条的每一步都可验证**，而且能推广到任何 `/proc` 文件、
任何计数器、任何 tracepoint。本教程的 labs/09 一直在用这个方法。

> 💡 **一个真实的小技巧**：如果你手上只有一台运行中的机器、
> 没有源码也没有网络，仍然可以从 `/boot/vmlinuz-$(uname -r)`
> 里把格式化字符串抠出来，从而确定"到底有几列、是不是十六进制"。
> 具体做法见
> [labs/09-observability/README.md 第 9 节](../labs/09-observability/README.md)。

### 4.6 用 printk / ftrace / bpftrace 验证猜想

读源码时经常会有"这里应该是这样吧"的猜想。**不要停在猜想上，去验证它。**

| 手段 | 适用场景 | 示例 |
|---|---|---|
| `pr_info()` / `pr_debug()`（+`dmesg`） | 最直接，但要重新编译/加载模块 | 在模块里打印 `sk->sk_state` |
| `dynamic_debug` | 免重编译打开已有的 `pr_debug` | `echo 'file tcp_input.c +p' > /sys/kernel/debug/dynamic_debug/control` |
| `trace_printk()` | 高频路径上比 `printk` 轻 | 但不能留在生产代码里 |
| **ftrace 事件** | 看内核已有的 tracepoint，**零改动** | `echo 1 > events/tcp/tcp_retransmit_skb/enable` |
| **ftrace function_graph** | 看真实调用链与每层耗时 | `echo function_graph > current_tracer` |
| **kprobe 事件** | 往任意函数插桩，**零改动** | `echo 'p:tcp tcp_v4_rcv' >> kprobe_events` |
| **bpftrace** | 聚合、直方图、按条件过滤 | `bpftrace -e 'kprobe:tcp_v4_rcv { @[comm]=count(); }'` |
| **QEMU + gdb** | 看某个变量为什么是那个值 | 断点 + `p sk->sk_state` |

**推荐的验证顺序**：tracepoint → function_graph → kprobe/bpftrace → gdb。
从"侵入性最小"到"侵入性最大"，因为内核网络代码大量跑在软中断里，
断点停太久会导致丢包甚至系统假死。

> ⚠️ 本机（`CapEff=0`、tracefs 只读、无 bpftrace/perf）**无法运行**这些手段。
> `labs/09-observability/06-tracepoint-templates.md` 里给出了完整模板与前置条件。

### 4.7 per-CPU 与 RCU 的阅读注意事项

内核网络代码为了性能大量使用 per-CPU 变量和无锁读（RCU）。
读代码时如果不注意，很容易得出错误结论。

#### per-CPU：看到 `this_cpu_*` 就要意识到"这不是全局值"

```c
// net/core/dev.c
this_cpu_inc(sd->dropped);              // 只加在"当前 CPU"的副本上
```

- **读的时候**必须遍历所有 CPU，否则你只看到一部分：

  ```c
  for_each_possible_cpu(cpu) {
      struct softnet_data *sd = per_cpu_ptr(&softnet_data, cpu);
      total += sd->dropped;
  }
  ```

- `/proc/net/softnet_stat` **每行一个 CPU**，就是这个原因。你 `cat` 出来的
  第一行是 CPU0 的数据，不是"总计"。
- **`this_cpu_inc` 通常是免锁的**（靠"关抢占"保证原子性），
  所以不要指望在它周围看到自旋锁。
- 常见 API：`this_cpu_inc/dec/add`、`per_cpu_ptr`、`get_cpu_var`/`put_cpu_var`、
  `for_each_possible_cpu` / `for_each_online_cpu`。
- ⚠️ 注意 `possible` 与 `online` 的区别：`possible` 包含**离线**的 CPU。
  `/proc/net/softnet_stat` 的行数通常等于 `possible` 的 CPU 数，
  可能**多于**当前在线核数（本机实测 20 行 / 20 核，刚好相等）。

#### RCU：看到 `rcu_read_lock` 要意识到"读到的可能正在被改"

```c
rcu_read_lock();
sk = __inet_lookup_established(...);   // 无锁查 hash 表
if (sk) { ... 使用 sk ... }             // 期间 sk 可能被别的 CPU 摘链
rcu_read_unlock();
```

- `rcu_read_lock()` **不是锁**，它不允许睡眠，也不阻塞写者；
  它只是保证"被 `rcu_dereference()` 拿到的对象在我读完之前不会被释放"。
- 写者要改结构时，会先让指针不可见（`rcu_assign_pointer`），
  然后等一个宽限期（`synchronize_rcu()`）才真正释放。
- 看到 `rcu_dereference()` / `rcu_assign_pointer()` / `synchronize_rcu()`
  这三兄弟，就知道这里在做 RCU。
- **读代码时的含义**：同时可能有多个 CPU 在改这张表，所以不要假设
  "我读到这里的值时，上面的判断仍然成立"，除非代码里有明确的
  `refcount_inc_not_zero()` 之类的再校验。

#### 其他并发阅读要点

- `READ_ONCE()` / `WRITE_ONCE()`：告诉编译器"这个值可能被并发修改，别优化"。
- `smp_rmb()` / `smp_wmb()`：内存屏障，通常和上面的宏成对出现。
- `spin_lock_bh()`：**关下半部**（软中断）的自旋锁。在收发路径上极常见，
  因为同一份数据可能同时被进程上下文和软中断访问。
  看到 `_bh` 后缀就要意识到"这里有进程上下文与软中断的竞争"。
- `local_bh_disable()`：单独关软中断（不加锁）。

### 4.8 如何判断一个函数跑在软中断还是进程上下文

这是读收包路径时**必须**搞清楚的事，因为它决定了：
能不能睡眠、能不能用 `mutex`、能不能分配内存、能调用哪些函数。

#### 方法 1：看代码里的上下文断言（最可靠）

```c
WARN_ON_ONCE(!in_softirq());        // 明确要求软中断上下文
might_sleep();                      // 声明"这里可能睡眠"，反过来说明
                                    // 不能在原子上下文调用
ASSERT_RTNL();                      // 要求持有 rtnl 锁（进程上下文）
```

`might_sleep()` 是最有用的信号：**如果一个函数里调用了 `might_sleep()`，
它就不能在软中断里被调用**；反过来，如果它在软中断里跑，
那它内部绝不能有 `might_sleep()`。

#### 方法 2：看函数用的辅助宏

| 宏 / 函数 | 含义 |
|---|---|
| `in_interrupt()` | 在**任何**中断上下文（硬中断 + 软中断 + NMI） |
| `in_softirq()` | 在软中断上下文（含被 `local_bh_disable()` 关下半部的进程上下文） |
| `in_serving_softirq()` | **确实正在执行**软中断（更严格，不含 `bh_disable`） |
| `in_task()` | 在进程上下文（**最常用**） |
| `in_atomic()` | 在原子上下文（不能睡眠） |
| `in_nmi()` | 在 NMI 上下文 |
| `preempt_count()` | 抢占计数；为 0 表示可以抢占（非原子） |

#### 方法 3：从调用链往上追到"根"

这是最实用的办法。判断标准是**最外层是谁调用的**：

| 起点 | 上下文 | 例子 |
|---|---|---|
| 系统调用（`SYSCALL_DEFINE*`） | 进程上下文 | `sendmsg` → `tcp_sendmsg` |
| 硬中断处理程序（`request_irq` 注册的 handler） | 硬中断 | 网卡中断入口（通常只做 `napi_schedule`） |
| `NET_RX_SOFTIRQ` / `NET_TX_SOFTIRQ` | 软中断 | `net_rx_action` → `napi_poll` |
| softirq 的线程化版本 | 进程上下文（但语义仍是"下半部"） | `ksoftirqd/N` 线程 |
| 内核线程 | 进程上下文 | `kworker`、`kswapd` |
| `timer_list` 回调 | 软中断 | `tcp_write_timer`（TCP 重传定时器） |
| workqueue | 进程上下文 | 可睡眠的延后工作 |

**几个具体结论**（背下来很有用）：

- 网卡**硬中断**处理程序（`ndo_*` 之外的 ISR）只做最少的事，
  通常就是 `napi_schedule()`，然后返回。**真正的收包在软中断里**。
- **NAPI poll（`napi_poll`）跑在软中断**（或 `ksoftirqd` 线程）里。
  所以 `netif_receive_skb` → `ip_rcv` → `tcp_v4_rcv` 整条收包链
  **默认都在软中断上下文**。
- **发包路径**（`tcp_sendmsg`）跑在**进程上下文**（系统调用里），
  但末尾的 `__qdisc_run` / 驱动发送可能落到 `NET_TX_SOFTIRQ`。
- **TCP 定时器**（重传、`TIME_WAIT`、`keepalive`）跑在**软中断**里
  （`timer_list` 回调）。
- 因此收包路径上的代码**不能睡眠**、不能 `mutex_lock`、不能
  用 `GFP_KERNEL` 分配内存。

#### 一个具体的判断练习

```bash
# 看看 ksoftirqd 是不是在忙（忙 = 软中断处理不过来）
ps -eLo pid,tid,comm,pcpu | grep -E 'ksoftirqd|PID'
# 本机若发现 ksoftirqd/N 长期占 CPU，说明收包压力已经溢出到线程化了
```

> 软中断与 `ksoftirqd` 的关系是：软中断**优先在中断返回路径上执行**
> （开销低）；如果执行太久或积压太多，内核会把它交给 `ksoftirqd/N` 内核线程。
> 所以 `ksoftirqd` 忙 = 软中断已经在"挤占"调度器了，是性能问题的信号。

关于"上下文"在观测中的体现，见
[docs/09 第 3 节](09-内核网络观测与性能调优.md)：
`softnet_stat` 第 3 列 `time_squeeze` 统计的正是
"软中断一次 poll 用完预算仍没处理完"的次数。

## 7. 权威资料

**遇到任何不确定的地方，按下面的优先级查证。**
优先级从高到低 —— 因为越靠前越"与你的内核一致"。

1. **你机器上的真实文件**（最高权威）
   - `/proc/net/*`、`/proc/sys/net/*` —— 运行内核的实时状态
   - `/sys/kernel/tracing/events/*/format` —— tracepoint 字段的最终定义
   - `/usr/src/linux-headers-$(uname -r)-common/include/uapi/` —— **与你内核同版本**
     的 uapi 结构体定义（本机可用，强烈推荐用来核对 netlink/结构体布局）
   - `man 7 tcp`、`man 7 socket`、`man 8 ss`、`man 8 ip`、`man 5 proc`
2. **你机器上内核的实际字符串**
   - `/boot/vmlinuz-$(uname -r)` 里能抠出格式串、错误信息、`printk` 文本
     （方法见 [labs/09 README 第 9 节](../labs/09-observability/README.md)）
3. **内核源码在线交叉引用**：<https://elixir.bootlin.com/linux/v6.12/source/>
4. **内核官方文档**（在源码树里，也可在 elixir 上看）
   - `Documentation/networking/` —— 网络子系统文档
   - `Documentation/admin-guide/sysctl/net.rst` —— **sysctl 的官方说明**（参数含义首选）
   - `Documentation/networking/scaling.rst` —— RPS/RFS、多队列
   - `Documentation/networking/segmentation-offloads.rst` —— GSO/GRO/TSO
   - `Documentation/trace/` —— ftrace
   - `Documentation/bpf/` —— BPF/bpftrace
   - `Documentation/networking/filter.rst` —— BPF 指令集
5. **RFC**：RFC 9293（TCP）、RFC 768（UDP）、RFC 791/8200（IPv4）、
   RFC 826（ARP）、RFC 9112（HTTP/1.1）
6. **书**
   - 《TCP/IP 详解 卷1：协议》—— 协议基础
   - 《Understanding Linux Network Internals》(Benvenuti) —— 内核网络经典，
     虽基于 2.6，但分层思想与数据结构仍然适用
   - 《深入理解 Linux 网络：架构设计与内核实现》—— 中文，覆盖较新内核
   - 《Linux 高性能服务器编程》—— 用户态高性能服务
   - 《BPF Performance Tools》(Brendan Gregg) —— eBPF 观测
7. **LWN.net** —— 内核新特性与设计讨论的最佳来源，搜 `<机制名> LWN`

> ⚠️ **本教程的准确性红线**：
> - 不写死内核代码**行号**（行号随版本变化，无意义且易错）。
> - 不确定的 `sysctl` **默认值不凭记忆写死**，而是给出读取命令
>   （`cat /proc/sys/net/...`）并注明"不同发行版/内核配置下可能不同"。
> - 遇到需要版本核对的细节，统一指向
>   <https://elixir.bootlin.com/linux/v6.12/source/> 并注明"以 6.12 为准"。

## 8. 小结

- **路线**：8 周系统路线（每章配实验）或 4 周速通路线（砍 lab 保主干）。
  选一条，坚持走完，比两条都试更有效。
- **环境**：三档。绝大多数内容在第 1 档（任意 Linux，无需 root）就能完成。
  本教程开发机就属于第 1 档为主、第 2 档部分可用（`CapEff=0` 但可用
  `unshare -Urnmpf` 拿到命名空间内能力），**第 3 档做不到**
  （没有 `/dev/net/tun`、不能 insmod、不能加载 eBPF、tracefs 只读）。
- **方法**：带着问题读源码，从已知锚点倒推调用链；
  用 ftrace/bpftrace/gdb 验证猜想；
  注意 per-CPU 与 RCU 带来的"看到的不是全部/不是最终值"；
  分清软中断与进程上下文。
- **纪律**：能跑的**真跑**，跑不了的**写清原因并优雅降级**，
  不确定的**指向可核查的来源**而不是编造。

准备好了的话，从 [docs/01 全景与数据流](01-Linux网络子系统全景与数据流.md) 开始。
如果你只有 30 分钟，先去 [labs/09-observability](../labs/09-observability/README.md)
跑一遍 `make run` —— 先看见，再理解。
