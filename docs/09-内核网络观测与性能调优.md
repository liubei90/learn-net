# 09 · 内核网络观测与性能调优

> 本章解决一个问题：**出问题时，怎么用一条可复现的路径把原因定位到具体的那一层。**
> 读完应能回答：① 丢包丢在哪一层（网卡/软中断/socket/应用），各看什么计数器？
> ② `ss`、`/proc/net/*`、`sysctl` 分别在什么场景用？③ 某个 `sysctl` 调大调小后果与风险？

## 0. 本章定位

[`docs/01`](01-Linux网络子系统全景与数据流.md) 给了地图，[`docs/05`](05-链路层-网卡驱动-NAPI与中断.md) 讲清了收包路径，本章把它们变成工具。配套实验是 [`labs/09-observability`](../labs/09-observability/README.md)（01–05、07 已在本机无 root 环境实测跑通）。

## 1. 观测方法论：从宏观到微观的排查漏斗

新手最常见的错误是**一上来就抓包**。抓包信息量太大，而且**看不到内核内部的丢弃**——在 softnet backlog 里就被丢掉的包，不会出现在任何抓包结果里。正确顺序是从便宜到昂贵：

```
第 0 层 应用层指标      QPS/延迟/P99，先确认"真的有问题吗、多严重"
第 1 层 汇总规模        ss -s：socket 总量、TIME-WAIT、孤儿数
第 2 层 socket 队列     ss -lnt / ss -tni 的 Send-Q / Recv-Q
第 3 层 TCP 计数器      /proc/net/snmp、/proc/net/netstat (TcpExt)
第 4 层 软中断与 backlog /proc/net/softnet_stat、/proc/softirqs
第 5 层 网卡与驱动      /sys/class/net/*/statistics/*、ip -s link、ethtool -S
第 6 层 内核 tracepoint ftrace / perf / bpftrace（最贵、最精确，需 root）
```

**三条纪律**：① **不要跳层**（第 2 层的 `Recv-Q` 能解释的问题不用动 tracepoint）；② 每层先看"有无异常"再看"异常多大"；③ 分清**累计值**（多数计数器，单次读数无意义，必须采样做差）与**瞬时值**（`CurrEstab`、队列长度）。

**先分清丢包与延迟是两类问题**：

| | 丢包类 | 延迟类 |
|---|---|---|
| 症状 | 吞吐上不去、超时、重传 | P99 高、抖动、偶发卡顿 |
| 首选 | 各层 `dropped` 计数器 | `ss -tni` 的 `rtt`/`rto`、`TCPTimeouts`、qdisc |
| 关键 | 丢在**哪一层** | 卡在**哪一段** |

高频误判：把"延迟高"当"丢包"。延迟高可能是发送缓冲太小导致的应用层排队（`TCP_NOTSENT_LOWAT`），而不是网络丢包；反过来"重传高"也不一定是丢包（见 case 6）。

**观测前先问**：① 丢的是 RX 还是 TX（两套独立计数器）？② 是少数连接还是所有连接（`ss -tni` 逐连接看）？③ **基线是什么**（没有基线的"看起来很大"无意义，要出问题前后各采一次做差）。

## 2. 关键指标与数据结构

### 2.1 三个队列：包到应用前要排三次队

这是"丢包丢在哪一层"的钥匙。三者**物理上不同、由不同代码管理、在不同条件下溢出**：

```
 ① 网卡 ring buffer（驱动层 DMA 环形缓冲）
    大小: ethtool -g/-G    溢出信号: rx_missed_errors / rx_fifo_errors
    原因: 内核取包速度 < 网卡收包速度
 ② softnet backlog（内核层，每 CPU 一个）
    大小: net.core.netdev_max_backlog
    溢出信号: /proc/net/softnet_stat 第 2 列 dropped
    原因: 软中断/NAPI 来不及消费（单核瓶颈最常见）
 ③ socket 接收队列（每 socket，数据已进 TCP 层）
    大小: SO_RCVBUF → net.core.rmem_max / net.ipv4.tcp_rmem
    溢出信号: TcpExt TCPRcvQDrop；ss 的 Recv-Q 持续 > 0
    原因: 应用 read()/recv() 太慢
```

> ⚠️ **重要澄清**：② 这个 backlog **只在特定路径被使用**。现代多队列网卡 + NAPI 的直接处理路径（`napi_poll` 里直接 `netif_receive_skb`）**不经过** backlog；它主要用于 RPS 开启时、非 NAPI 驱动、以及把包"推后处理"的场景。所以 `softnet_stat` 第 2 列全 0 而仍在丢包是**正常的**——说明丢包不在这一层（详见 case 2）。

### 2.2 观测接口与内核数据结构的对应

| 观测接口 | 内核结构 / 函数 | 性质 | 粒度 |
|---|---|---|---|
| `ss` / `/proc/net/tcp` | `struct sock`、`struct tcp_sock`、`struct inet_connection_sock` | 瞬时 | 每 socket |
| `/proc/net/snmp` | `netns_mib.tcp_statistics`（`TCP_MIB_*`） | 累计 | 每 netns |
| `/proc/net/netstat` | `netns_mib.tcp_ext`（`LINUX_MIB_TCPEXT_*`） | 累计 | 每 netns |
| `/proc/net/softnet_stat` | `struct softnet_data`（**每 CPU**） | 累计 | 每 CPU |
| `/proc/net/sockstat` | 各协议 hash 表统计 | 瞬时 | 全局 |
| `/sys/class/net/*/statistics/*` | `struct rtnl_link_stats64` | 累计 | 每网卡 |
| `/proc/interrupts`、`/proc/softirqs` | 中断/软中断描述符 | 累计 | 每 IRQ/类型 × 每 CPU |
| `ethtool -S` | 驱动私有计数器 | 累计 | 每网卡队列 |
| tracepoint | 内核埋点 | 事件 | 每事件 |

**三个必须记住的性质**：① **per-CPU 计数器必须每 CPU 都看**——`softnet_stat` 第 1 行不是"总计"；一个 CPU 的 `dropped` 高和其他为 0 是**完全不同**的问题（前者是亲和性/均衡问题，后者是整体能力不足）。② **`mem` 类字段单位常是"页"**（本机 4096 字节），如 `sockstat` 的 `mem`、`tcp_mem`/`udp_mem`、`protocols` 的 `memory`。③ **十六进制**——`/proc/net/tcp` 的地址/端口/队列、`softnet_stat` 所有列、`/proc/net/route` 的地址全是十六进制。

### 2.3 `/proc/net/*` 逐文件解释

这些文件本机**全部可读（实测 16/16）**且大多**不需要 root**，是"没有权限也能观测内核"的核心资产。

**`dev`**：每张网卡的收发统计。字段顺序固定：接收 `bytes packets errs drop fifo frame compressed multicast`，发送 `bytes packets errs drop fifo colls carrier compressed`；第 3 行起每行以 `接口名:` 开头。是 `struct rtnl_link_stats64` 的文本视图，与 `/sys/class/net/<if>/statistics/` 同源。本机实测含 `lo`、`wlan0`、`docker0` 等。

**`snmp`**：协议级 MIB。**格式特殊：奇数行是字段名，偶数行是对应值，按前缀成对出现**。本机 `Tcp:` 行实测：`RtoAlgorithm RtoMin RtoMax MaxConn ActiveOpens PassiveOpens AttemptFails EstabResets CurrEstab InSegs OutSegs RetransSegs InErrs OutRsts InCsumErrors`。

| `Tcp:` 字段 | 含义 | 本机实测 |
|---|---|---|
| `ActiveOpens` / `PassiveOpens` | 主动/被动建连数（判断本机角色） | 7393 / 1531 |
| `AttemptFails` / `EstabResets` | 建连失败 / 已建立连接被 RST | 122 / 829 |
| `CurrEstab` | 当前 ESTABLISHED（**瞬时值**） | 483 |
| `InSegs` / `OutSegs` / `RetransSegs` | 收/发/重传报文段 | 19770750 / 18964484 / 2813 |
| `InErrs` / `OutRsts` / `InCsumErrors` | 错误段 / 发出 RST / 校验和错误 | 6 / 1582 / 0 |

**`netstat`**：扩展 MIB。本机实测 3 组：`TcpExt`（**132 个**计数器）、`IpExt`、`MPTcpExt`，同为"名字行 + 值行"。`TcpExt` 是丢包排查主战场，详见第 6 节。

**`sockstat`**：socket 数量与内存。实测 `sockets: used 1669`、`TCP: inuse 510 orphan 3 tw 15 alloc 526 mem 120`、`UDP: inuse 7 mem 5`。`orphan` = 应用已 `close()` 但内核还在用（**持续增长 = 发送慢或对端不收**）；`tw` = TIME-WAIT 数；**`mem` 单位是页**。

**`tcp` / `tcp6`**：TCP socket 表，**全部十六进制**。实测样例：

```
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 0100007F:A171 00000000:0000 0A 00000000:00000000 00:00000000 00000000  1000        0 321919
   6: 0100007F:EAEC 0100007F:0C08 01 00000000:00000000 02:00000025 00000000  1000        0 285957
```

- `local_address` = `HEX_IP:HEX_PORT`，IP 是**小端**：`0100007F` → `127.0.0.1`，`0C08` = 3080（可与 `ss` 交叉验证：本机确实在 `127.0.0.1:3080` 监听）。
- `st` = 状态码（来自 `include/net/tcp_states.h` 的 `enum { TCP_ESTABLISHED = 1, ... }`）：`01`=ESTABLISHED、`02`=SYN_SENT、`03`=SYN_RECV、`04`=FIN_WAIT1、`05`=FIN_WAIT2、`06`=TIME_WAIT、`07`=CLOSE、`08`=CLOSE_WAIT、`09`=LAST_ACK、`0A`=LISTEN、`0B`=CLOSING、`0C`=NEW_SYN_RECV。
- `tx_queue:rx_queue` = `ss` 的 `Send-Q:Recv-Q`（也是十六进制）；`inode` 可与 `/proc/<pid>/fd/` 的 `socket:[inode]` 对应以定位进程。

**`udp` / `udp6`**：格式同上，但 `st` 几乎总是 `07`(CLOSE)，除非该 socket `connect()` 过（此时显示 `01`——本机实测有一个 DHCP 客户端 socket 就是这种"已连接的 UDP"）。UDP 丢包主要看 `drops` 列与 `snmp` 的 `Udp:` 组 `RcvbufErrors`/`SndbufErrors`。

**`raw` / `raw6`**：`SOCK_RAW` 表。本机 `RAW: inuse 1`（IPv6 侧）。创建原始套接字需 `CAP_NET_RAW`，普通用户这里通常是空的。

**`arp`**：IPv4 邻居表。实测 `10.0.0.1  0x1  0x2  00:11:22:33:44:04  *  wlan0`。`Flags` 的 `0x2` = `ATF_COM`（条目完整）；`0x0` = 不完整（对应 `NUD_INCOMPLETE`）。

**`route`**：IPv4 路由表，**十六进制 + 小端**。实测 `wlan0 00000000 011FA8C0 0003 ... 00000000` 与 `wlan0 001FA8C0 00000000 0001 ... 00FFFFFF`。`00000000` 是默认路由；`011FA8C0` 小端读 = `10.0.0.1`（与 `arp` 里的网关一致）；`00FFFFFF` = `/24`；`Flags 0003` = `RTF_UP|RTF_GATEWAY`。

**`fib_trie`**：**路由查找用的数据结构本身**（LC-trie），不是给人看的表格。实测片段：

```
Main:
  +-- 0.0.0.0/0 3 0 4
     |-- 0.0.0.0
        /0 universe UNICAST
     +-- 127.0.0.0/8 2 0 2
        |-- 127.0.0.1
           /32 host LOCAL
```

`universe` = 路由可全局使用，`host LOCAL` = 本机地址，`link BROADCAST` = 广播地址。它是理解"为什么路由查找是 O(log n) 而非线性扫描"的最好材料（`/proc/net/fib_triestat` 有统计）。

**`softnet_stat`**：**丢包排查第一现场**。实测样例行：

```
000a5e9f 00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000 ...
```

**本机实测每行 15 列，全部是 8 位十六进制**（`000a5e9f` = 十进制的 679583，**不是**一千万）。

| 列 | 名称 | 置信度 | 说明 |
|---|---|---|---|
| 1 | `processed` | 已确认 | 该 CPU 处理的报文总数 |
| 2 | `dropped` | 已确认 | **因 backlog 队列满而丢弃** ★关键 |
| 3 | `time_squeeze` | 已确认 | 一次 NAPI poll 用光预算仍没处理完的次数 ★关键 |
| 4–8 | 保留 | 待核对 | 历史上是 `fastroute`，现恒为 0 |
| 9 | 保留 | 待核对 | 历史上是 `cpu_collision`，现恒为 0 |
| 10 | `received_rps` | 待核对 | RPS 触发次数 |
| 11 | `flow_limit_count` | 待核对 | RFS flow limit 触发次数 |
| 12–15 | 保留 | 待核对 | 保留位 |

> ⚠️ **为什么第 4 列之后标"待核对"**：本机无内核源码树也无网络，读不到 `net/core/net-procfs.c` 中 `softnet_seq_show()` 传给 `seq_printf` 的**参数顺序**。作者用取巧办法确认了"**是 15 列、全是 `%08x`**"——从运行中的内核镜像 `/boot/vmlinuz-$(uname -r)` 里抠出格式串（复现方法见 [labs/09 README 第 9 节](../labs/09-observability/README.md)）——但**列与结构体字段的对应关系**必须以源码为准：`elixir.bootlin.com/linux/v6.12/source/net/core/net-procfs.c`，结构体 `struct softnet_data` 定义在 `include/linux/netdevice.h`。
> **这也说明列数会随内核版本变化**。先 `awk 'NR==1{print NF}' /proc/net/softnet_stat` 数一下你的列数，再读对应版本源码，不要照搬任何博客的列名表。

**`netlink`**：内核里的 `AF_NETLINK` socket 表（`ss`/`ip` 通信依赖它）。排查 netlink 接收队列溢出（`ENOBUFS`）时有用。

**`packet`**：`AF_PACKET` socket 表（tcpdump/libpcap 用它）。本机无 `CAP_NET_RAW`，通常为空。列含 `RefCnt`/`Type`/`Iface`/`Rmem`/`Rcvbuf`。

**`protocols`**：各传输层协议的内存与回调表。实测表头 `protocol size sockets memory press maxhdr slab module cl co di ac io in de sh ss gs se re bi br ha uh gp em`。`size` = 该协议 `struct sock` 大小（判断内存量级）；`memory` = 当前缓冲内存（**页**，`-1` 表示不上报）；最后那串 `y`/`n` 是**回调能力矩阵**（对应 `struct proto_ops` 各项是否实现），排查"某操作在此协议上不支持"很有用。

**`unix`**：Unix domain socket 表。实测 `Num RefCount Protocol Flags Type St Inode Path`。`St` 的 `03` = SS_CONNECTED、`01` = SS_UNCONNECTED；`Type` 的 `0001` = `SOCK_STREAM`、`0002` = `SOCK_DGRAM`、`0005` = `SOCK_SEQPACKET`。本地 RPC 变慢时是直接证据。

## 3. 数据流视角下的可观测点

### 3.1 接收路径（RX）

```
 网卡硬件: 包到达 → DMA 写入 ring buffer
      │ ① ring 满 = 驱动级丢包
      │    看: rx_missed_errors / rx_fifo_errors / ethtool -S（需 root）
      ▼
 napi_schedule()   ← 硬中断只做这一件事
      │ ② 中断计数: /proc/interrupts
      ▼ ─── NET_RX_SOFTIRQ（软中断上下文）───
 net_rx_action()   预算: netdev_budget / netdev_budget_usecs
      │ ③ 预算耗尽 → time_squeeze++
      │    看: softnet_stat 第 3 列、/proc/softirqs 的 NET_RX
      ▼
 napi_poll() → 驱动 poll → 收 ring 里的包
      ├─[backlog 路径] enqueue_to_backlog()
      │    ④ 队列满 → dropped++   看: softnet_stat 第 2 列 ★最关键
      │       调: net.core.netdev_max_backlog
      └─[直接路径] napi_gro_receive() → GRO 合并 → netif_receive_skb()
            │ ⑤ 协议分发 ptype_base   看: /proc/net/ptype
            ▼
        ip_rcv() → NF_INET_PRE_ROUTING → ip_rcv_finish() → 路由查找
            │ ⑥ 路由失败   看: snmp 的 Ip: 组 InAddrErrors/OutNoRoutes
            ▼
        ip_local_deliver() → NF_INET_LOCAL_IN → tcp_v4_rcv()
            │ ⑦ 找不到 socket → 发 RST；原因看 skb:kfree_skb 的 reason
            ├─→ tcp_rcv_established()    数据快路径
            └─→ tcp_rcv_state_process()  握手/挥手
                  │ ⑧ 全连接队列溢出   看: TcpExt ListenOverflows/ListenDrops ★
                  │    半连接队列满     看: TcpExt TCPReqQFullDrop
                  ▼
               数据入 sk->sk_receive_queue
                  │ ⑨ 接收队列满 → 丢包
                  │    看: TcpExt TCPRcvQDrop ★；ss 的 Recv-Q ← 最直观
                  ▼
               sk_data_ready() → 唤醒 epoll/阻塞进程 → 应用 recv()
                  │ ⑩ 应用读取慢 → Recv-Q 持高
```

**使用方法**：遇到问题从上往下（或从下往上）逐个检查 ①–⑩，**第一个出现异常的层就是根因所在层**。

### 3.2 发送路径（TX）

```
应用 send() │ ① 发送缓冲满 → 阻塞/EAGAIN   看: ss -tm 的 skmem w(已排队)/wb(上限)
 tcp_sendmsg() → sk_write_queue
            │ ② 拥塞窗口满 → 积压   看: ss -tni 的 cwnd/unacked/snd_wnd ★
 tcp_write_xmit() → __tcp_transmit_skb() → ip_queue_xmit()
            │ ③ NF_INET_LOCAL_OUT/POST_ROUTING；④ 路由失败 → OutNoRoutes
 qdisc（默认 fq_codel）│ ⑤ 队列满 → tx_dropped   看: /proc/net/dev 的 tx drop
 驱动 ndo_start_xmit → 网卡 TX ring │ ⑥ ring 满 → tx_fifo_errors
```

发送方向判断最简单：**看 `ss -tni` 的 `cwnd` 与 `unacked`**。若 `unacked` 长期 ≈ `cwnd` 且 `cwnd` 很小 → 发送被拥塞窗口卡住（网络丢包或 RTT 大）；若队列正常但应用仍阻塞在 `send()` → 发送缓冲区（`SO_SNDBUF`）太小。

### 3.3 连接生命周期

```
CLOSED → [SYN queue 满 → TCPReqQFullDrop / TCPReqQFullDoCookies]
       → SYN_SENT/SYN_RECV → ESTABLISHED
            [accept queue 满 → ListenOverflows / ListenDrops]
       → 数据交换 [重传 → RetransSegs / TCPTimeouts / TCPLostRetransmit]
       → FIN_WAIT1/2、CLOSE_WAIT、LAST_ACK
       → TIME_WAIT [溢出 → TCPTimeWaitOverflow；端口耗尽 → EADDRNOTAVAIL]
       → CLOSED
```

用 [`07-watch-tcp-state.sh`](../labs/09-observability/07-watch-tcp-state.sh) 可把生命周期"随时间"看出来（轮询 `/proc/net/tcp` 统计各状态数量）。本机实测：

```
  STATE \ 采样点       #1       #2       #3       #4     变化
  ESTABLISHED         478      478      478      478          0
  SYN_SENT              8        8        8        8          0
  TIME_WAIT            10        8        8        8         -2
  CLOSE_WAIT            5        5        5        5          0
  LISTEN                8        8        8        8          0
  TOTAL               511      509      509      509         -2
```

> ⚠️ **固有局限**：`/proc/net/tcp` 是**轮询快照**而非事件流，两次采样之间"建立又立刻关闭"的短连接会被完全漏掉。它擅长发现**堆积/泄漏**（如 `CLOSE_WAIT` 单调增长 = 应用忘了 `close()`），**不擅长**发现高频短连接——那必须用 `sock:inet_sock_set_state` tracepoint（本机无权限，模板见 [labs/09 的 06](../labs/09-observability/06-tracepoint-templates.md)）。

## 4. 观测命令与工具矩阵

### 4.1 工具选择速查

| 想回答 | 命令 | 需 root |
|---|---|---|
| socket 总量与分布 | `ss -s` | 否 |
| 谁在监听、accept 队列积压 | `ss -lntp` | 否（`-p` 只看自己的进程） |
| 哪条连接有问题（RTT/cwnd/重传） | `ss -tni` | 否 |
| socket 内存用在哪 | `ss -tm` | 否 |
| 定时器还有多久到期 | `ss -to` | 否 |
| 哪些连接在 CLOSE_WAIT 堆积 | `ss -tn state close-wait` | 否 |
| 协议栈各层计数器 | `cat /proc/net/snmp`、`/proc/net/netstat` | 否 |
| 软中断处理不过来 | `cat /proc/net/softnet_stat`、`/proc/softirqs` | 否 |
| 网卡驱动/ring 丢包 | `ethtool -S`、`ethtool -g` | **是** |
| 内核里到底发生了什么事件 | ftrace / perf / bpftrace | **是** |

### 4.2 `ss` 的进阶用法

`ss` 是 `NETLINK_SOCK_DIAG` 的客户端（**不是**读 `/proc`），所以能拿到 `/proc/net/tcp` 里**没有**的字段。本机版本 `iproute2-6.15.0`。

```bash
ss -s                       # ① 汇总：总量与内存。第一步永远是这个
ss -lntp                    # ② 监听端口 + 进程
ss -tni                     # ③ 内核内部信息（最有用）
ss -tm                      # ④ 内存占用（skmem）
ss -to                      # ⑤ 定时器
ss -tie                     # ⑥ 扩展信息（cgroup/UID/inode）
ss -tn state close-wait     # ⑦ 只看特定状态（排查堆积首选）
ss -tn state time-wait
ss -K dst 10.0.0.1 dport = 80   # ⑧ 强制关闭 socket（危险，需 root）
ss -tn '( sport = :80 or sport = :443 )'   # ⑨ C 风格过滤表达式
ss --tcp-info 2>/dev/null || ss -ti        # ⑩ TCP 内部扩展
```

**③ `ss -tni` 的字段**（本机真实输出片段，对照 `include/uapi/linux/tcp.h` 的 `struct tcp_info`）：

```
ESTAB 0 0 127.0.0.1:60140 127.0.0.1:3080
  cubic wscale:7,7 rto:204 rtt:0.057/0.031 ato:40 mss:36992 cwnd:10
  bytes_sent:1307 bytes_acked:1308 segs_out:40423 app_limited
  rcv_space:65495 rcv_ssthresh:97308 minrtt:0.018 snd_wnd:73984 rcv_wnd:97408
```

`cubic`=拥塞算法；`rtt:A/B`=平滑 RTT/抖动（毫秒）；`rto`=重传超时（毫秒）；`cwnd`=拥塞窗口；`ssthresh`=慢启动阈值；`unacked`=已发未确认；`retrans`=重传；**`app_limited`=发送受限于应用而非网络 ★**；`snd_wnd`/`rcv_wnd`=发送/接收窗口。

**④ `ss -tm` 的 `skmem` 九个字段**（本机真实输出 `skmem:(r0,rb131072,t0,tb2626560,f0,w0,o0,bl0,d0)`；字段含义来自本机 `man ss`，权威）：

| 字段 | 含义 | 字段 | 含义 |
|---|---|---|---|
| `r` | `rmem_alloc` 已分配接收缓冲 | `w` | `wmem_queued` **已排队待发的字节数 ★** |
| `rb` | `rcv_buf` 接收缓冲上限 | `o` | `opt_mem` sockopt 内存 |
| `t` | `wmem_alloc` 已使用的发送缓冲 | `bl` | `back_log` **全连接队列长度 ★** |
| `tb` | `snd_buf` 发送缓冲上限 | `d` | `sock_drop` **该 socket 丢弃的包数 ★** |
| `f` | `fwd_alloc` 作为缓存预留但未使用 | | |

**⑤ `ss -to`**：实测 `timer:(keepalive,780ms,0)`。类型有 `on`(重传)/`keepalive`/`timewait`/`retrans`。

**⑥ `ss -tie`**：⚠️ 本机实测会打印若干行 `Failed to open cgroup2 by ID`——当前环境读不到 cgroup2 信息。这是环境限制，不影响其他列；**必须知道这点，否则会误以为 ss 坏了**。

**⑧ `ss -K`**：本机无法运行（无权限）——"内核提供了能力但非特权拿不到"的典型例子。

> 📌 **`app_limited` 值得单独记住**：出现它说明**发送速率受限于应用产生数据的速度**，而非网络。此时再调拥塞控制/缓冲区都无效——瓶颈在应用侧。这是"误判重灾区"（见 case 6）。

### 4.3 `/proc/softirqs` 与 `/proc/interrupts`

```bash
cat /proc/softirqs     # 每 CPU 一列，关注 NET_RX/NET_TX 的分布
cat /proc/interrupts   # 每 IRQ 一行、每 CPU 一列，看网卡中断是否集中
```

**都是累计值**。判断"是否均衡"应比较同一时刻的相对比例，或采样两次做差。若 `NET_RX` 在 CPU0 远高于其他 → 单核瓶颈，考虑 RPS/多队列。本机实测 `softnet_stat` 有 20 行 / 20 个在线 CPU。

### 4.4 完整"体检"序列（全部不需要 root，本机已实测）

```bash
ss -s && ss -lntp                                    # 宏观
ss -tn state close-wait | head                       # 队列积压
grep '^Tcp:' /proc/net/snmp                          # 协议计数器
awk 'NR<=2' /proc/net/netstat | head -c 2000         # TcpExt
cat /proc/net/sockstat
awk '{print NR-1, $1, $2, $3}' /proc/net/softnet_stat  # 需转十六进制，见 labs/09 的 03
ip -s link
for d in /sys/class/net/*; do printf '%-12s rx_drop=%s tx_drop=%s rx_err=%s rx_missed=%s\n' \
  "$(basename $d)" "$(cat $d/statistics/rx_dropped 2>/dev/null || echo -)" \
  "$(cat $d/statistics/tx_dropped 2>/dev/null || echo -)" \
  "$(cat $d/statistics/rx_errors 2>/dev/null || echo -)" \
  "$(cat $d/statistics/rx_missed_errors 2>/dev/null || echo n/a)"; done
```

本教程把上述封装为 [`labs/09-observability`](../labs/09-observability/README.md) 的 03、04 脚本，`make run` 可直接跑。

### 4.5 容器与虚拟化环境的观测差异

**① `/proc/net/*` 与 `/proc/sys/net/*` 是"命名空间视图"**。这两棵树是 **per-netns** 的：容器里 `cat /proc/net/dev` 只看得到本 netns 的网卡（通常 `lo` + `eth0`/`veth`）。`/proc/net/snmp` 的 MIB 也是 per-netns 的，所以"容器里看不到丢包"**不代表**宿主机没丢。判断物理网卡/软中断层问题**必须到宿主机上看**。

**② veth 成对，统计要两端对照**。容器内 `eth0` 的 **TX** 应大致等于宿主机 `vethXXX` 的 **RX**；对不上就找到了丢包的一侧。找宿主机侧的名字：

```bash
cat /sys/class/net/eth0/iflink       # 容器内取 ifindex，如 12
ip -d link show | grep -B2 'iflink 12'   # 宿主机上对应 vetha1b2c3
```

**③ cgroup 统计是另一个维度，且容易误解**。`ss -e` 的 cgroup 列来自 `INET_DIAG_CGROUP_ID`；**本机实测 `ss -e` 报 `Failed to open cgroup2 by ID`**。关键澄清：**cgroup v2 没有内置的"按 cgroup 统计网络流量"**。容器网络流量的来源通常是 (a) 读 veth 的 `/sys/class/net/*/statistics/`，(b) 用 eBPF（如 Cilium）在内核按 cgroup/pod 聚合。

**④ netns 隔离**：`ss`/`ip` 看到的都是本 netns；看别的 netns 需 `ip netns exec <ns> ss -s`（需 root）。容器通常无 `CAP_NET_ADMIN`，连 `ip netns list` 都不可用。

**⑤ K8s 方案速查**：

| 需求 | 方案 |
|---|---|
| 节点级指标 | `node-exporter`（暴露 `/proc/net/*`、`/sys/class/net/*`） |
| Pod 级流量 | eBPF（Cilium/Hubble）在内核按 cgroup 聚合 |
| 单 Pod 排障 | `kubectl debug` 注入带 `ss`/`nsenter` 的容器；或 `nsenter -t <pid> -n ss -s` |
| 连接级追踪 | `sock:inet_sock_set_state` + eBPF |

> **实用原则**：在容器里诊断时先问"**这个问题属于哪个 netns**"。属于容器 netns 的（应用读取慢、socket 队列、容器内端口耗尽）→ 在容器里看；属于宿主机 netns 的（物理网卡 ring、softnet backlog、网卡中断）→ **必须到宿主机看**，容器里看多少遍也没用。

## 5. `sysctl` 调优表

### 5.0 读法

```bash
sysctl -n net.core.somaxconn          # 方式 1（需要 procps）
cat /proc/sys/net/core/somaxconn      # 方式 2（总是可用，名字里的 . 换成 /）
sysctl -w net.core.somaxconn=4096     # 写（需 root）；持久化写 /etc/sysctl.d/99-net.conf
```

> 📌 **关于 `sysctl` 命令**：本机确实装了 sysctl（`procps` 包提供 `/usr/sbin/sysctl`），
> 但它所在目录不在当前非登录 shell 的 `PATH` 里，直接敲 `sysctl` 会得到「未找到命令」。
> 这是一个**易被误判为「没装」的环境陷阱**。本教程一律用方式 2（`cat /proc/sys/...`），
> 因为它在任何环境、任何权限下都能用，不需要 `PATH` 或 root。
> 两者读取的是同一份数据；用 [`scripts/env-check.sh`](../scripts/env-check.sh) 可一次打印全部只读快照。
> ⚠️ 下表的"本机实测值"是采集时刻的**真实读数，不是内核默认值**。请读你自己机器的值。语义以 `Documentation/admin-guide/sysctl/net.rst` 为准。

### 5.1 连接队列

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.core.somaxconn` | `4096` | **全连接队列**上限，与 `listen(fd, backlog)` 取**较小值** | 调大抗突发、减少 `ListenOverflows` | ⚠️ 只改它而不改应用 `listen()` 的 backlog 往往**完全无效**（取 min）。改大后若应用不 `accept()`，只是把丢弃推迟且更耗内存 |
| `net.ipv4.tcp_max_syn_backlog` | `2048` | **半连接队列**（SYN queue）上限 | 调大抗 SYN 洪峰 | ⚠️ 只在 `tcp_syncookies=0` 时才是硬上限。**不要**为"防 SYN Flood"盲目调大，syncookies 才是正解 |
| `net.ipv4.tcp_syncookies` | `1` | 半连接队列满时把状态编码进 SYN-ACK 序列号 | `1` 推荐（仅队列满时启用）；`2` 强制总是使用 | ⚠️ 开启后看不到 `TCPReqQFullDrop` 增长，而是 `TCPReqQFullDoCookies`——别以为"没丢包就没事"。会牺牲部分 TCP 选项（如窗口缩放） |
| `net.ipv4.tcp_abort_on_overflow` | `0` | 全连接队列满时：静默丢 ACK（0）/ 回 RST（1） | `1` 让问题更早暴露但用户看到"连接被拒" | ⚠️ 排查阶段可临时设 1 确认是否队列溢出，生产环境设 1 体验更差 |

### 5.2 端口与 TIME-WAIT

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.ipv4.ip_local_port_range` | `32768 60999` | 客户端**临时端口**范围 | 调大范围缓解端口耗尽 | ⚠️ 不要覆盖监听端口与 `ip_local_reserved_ports`；上限超过 65535 无意义。调大只治标 |
| `net.ipv4.tcp_tw_reuse` | `2` | 允许**主动方**在安全前提下复用 TIME-WAIT 端口发起新连接 | 开启可减少客户端端口耗尽 | ⚠️ 类型是 `u8`（`include/net/netns/ipv4.h`），取值 0/1/2，本机为 2；**各取值的精确语义在本机无法确证**，请以 6.12 源码中判断该参数的分支为准（`net/ipv4/tcp_ipv4.c`）。**只对"主动发起连接"一方有效，对服务端 TIME-WAIT 堆积无效** |
| `net.ipv4.tcp_fin_timeout` | `60` | FIN_WAIT2 超时（秒） | 调小更快回收 FIN_WAIT2 | ⚠️ **它不控制 TIME-WAIT 时长**（TIME-WAIT 固定 2MSL、不可调）。这是最经典的误用：想缩短 TIME-WAIT 却改这个参数，毫无效果 |
| `net.ipv4.tcp_max_tw_buckets` | `131072` | 系统同时存在的 TIME-WAIT 上限，超出立即销毁并打日志 | 调大容忍更多 TIME-WAIT | ⚠️ 超出日志为 `time wait bucket table overflow`（计数器 `TCPTimeWaitOverflow`）。**调小它来"解决 TIME-WAIT 太多"是危险的**——会破坏 TIME-WAIT 的保护语义 |
| `net.ipv4.tcp_max_orphans` | `131072` | 不属于任何进程的 socket 上限 | 调大容忍更多孤儿 | ⚠️ 超限会打 `Out of socket memory` 并 reset 连接。**`orphan` 持续增长说明发送慢/对端不收**，调参数只是掩盖症状 |

### 5.3 socket 缓冲区

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.core.rmem_default` | `212992` | 接收缓冲**默认值**（字节） | 调大默认给更多缓冲 | ⚠️ 必须 ≤ `rmem_max` |
| `net.core.rmem_max` | `212992` | `SO_RCVBUF` 可设的**最大值** | 调大后应用才能设更大接收缓冲（大 BDP 链路必需） | ⚠️ **只调它不够，应用必须显式 `setsockopt(SO_RCVBUF)`**。另受 `tcp_rmem` 第三值约束。⚠️ 现代内核会把它**翻倍**（TCP 用一半做开销），"设 1MB 看到 2MB"是正常的 |
| `net.core.wmem_default` | `212992` | 发送缓冲默认值 | 同上 | 同上 |
| `net.core.wmem_max` | `212992` | `SO_SNDBUF` 可设的最大值 | 调大提升大流量吞吐 | ⚠️ 发送缓冲太大会**增加延迟**（数据先排队再发）；延迟敏感业务应调小或用 `TCP_NOTSENT_LOWAT` |
| `net.ipv4.tcp_rmem` | `4096 131072 6291456` | TCP 接收缓冲 **min / default / max** | 调大 max 支持大 BDP 链路 | ⚠️ 内核在 min–max 间**自动调整**（受 `tcp_moderate_rcvbuf` 控制）。改 middle 值只影响新建连接的起点，不改自动调整范围 |
| `net.ipv4.tcp_wmem` | `4096 16384 4194304` | TCP 发送缓冲 min/default/max | 同上 | ⚠️ 与 `tcp_rmem` 不同，发送缓冲不自动无界增长，受拥塞窗口约束。**缓冲至少要 ≥ BDP（带宽×RTT）**，否则吞吐上不去 |
| `net.ipv4.tcp_moderate_rcvbuf` | `1` | 接收缓冲**自动调整**开关 | `1` 推荐 | ⚠️ 设 `0` 会**显著降低**大带宽场景吞吐（等于放弃自动调优） |
| `net.ipv4.tcp_mem` | `282705 376942 565410` | TCP **全局**内存 low/pressure/max（**单位页**） | 调大容忍更多 TCP 内存 | ⚠️ **单位是页**（4096 字节/页），`282705` 页 ≈ 1.1 GB。误把页当字节是最经典错误。超过 pressure 开始回收，超过 max 拒绝新连接（`TCPAbortOnMemory`/`TCPMemoryPressures` 增长） |
| `net.ipv4.udp_mem` | `565413 753884 1130826` | UDP 全局内存阈值（页） | 同上 | ⚠️ UDP 无重传，超限**直接丢包且不通知应用**；盯 `Udp: RcvbufErrors` |
| `net.core.optmem_max` | `131072` | 每 socket 的**辅助数据**（`cmsghdr`）上限 | 调大支持更多控制消息 | ⚠️ 遇到 `sendmsg` 返回 `ENOBUFS` 时考虑它，但**它不是数据缓冲区**（那是 rmem/wmem） |

### 5.4 拥塞控制与 qdisc

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.ipv4.tcp_congestion_control` | `cubic` | 默认拥塞控制算法 | 可换 `reno`/`bbr`/`dctcp`（需先加载模块） | ⚠️ `bbr` 在有丢包链路吞吐更好，但可能"抢占"其他 CUBIC 流带宽、在浅缓冲设备上造成排队延迟。**换算法前先确认路径设备行为** |
| `net.ipv4.tcp_available_congestion_control` | `reno cubic` | 可用算法列表（**只读**） | 改不了 | ⚠️ 想用 `bbr` 却不在列表 → 需 `modprobe tcp_bbr` |
| `net.core.default_qdisc` | `fq_codel` | 默认排队规则 | `fq_codel`（低延迟）、`fq`（配合 BBR）、`pfifo_fast` | ⚠️ **只对新建 qdisc 生效**，已有接口需 `tc qdisc replace`。`fq` 是为配合 BBR 做 pacing，配 CUBIC 收益有限 |
| `net.ipv4.tcp_slow_start_after_idle` | `1` | 空闲后是否把 `cwnd` 重置回初始值 | 设 `0` 对长连接间歇发送有利（如数据库） | ⚠️ 设 `0` 对动态变化网络可能过于激进 |
| `net.ipv4.tcp_notsent_lowat` | `4294967295` | 发送队列中"未发送数据"水位上限 | 调**小**（如 128KB）可降尾延迟 | ⚠️ 本机 `4294967295` = `UINT_MAX`，等于禁用。降低会牺牲吞吐。**别把它当"缓冲区大小"** |
| `net.ipv4.tcp_mtu_probing` | `0` | 自动探测路径 MTU | `1` 仅探测黑洞；`2` 总是探测 | ⚠️ 仅确认存在 PMTU 黑洞（大包不通、小包通）时开启，有额外探测流量 |
| `net.ipv4.tcp_fastopen` | `1` | TCP Fast Open：SYN 里捎带数据 | **位掩码**：`1`=客户端启用、`2`=服务端启用、`4`=客户端无 cookie 也发数据，另有 `0x200`/`0x400` 服务端标志 | ⚠️ 本机 `1` = **只启用客户端**。要服务端支持须设成含 `2` 的值（如 `3`）**且应用显式 `setsockopt(TCP_FASTOPEN)`**。位标志定义见 `include/net/tcp.h` 的 `Bit Flags for sysctl_tcp_fastopen`。这类位掩码参数最易被当布尔值误用 |
| `net.ipv4.tcp_ecn` | `2` | 显式拥塞通知 | `0` 关闭；非 0 按模式启用 | ⚠️ 类型 `u8`。ECN 对端/中间设备支持不一致，曾有"ECN 导致连接异常"案例。语义以 `sysctl/net.rst` 为准 |
| `net.ipv4.tcp_window_scaling` | `1` | 窗口缩放（RFC 7323），大 BDP 必需 | 保持 `1` | ⚠️ 关闭会让窗口上限降到 64KB，**严重**限制高带宽高延迟链路吞吐 |
| `net.ipv4.tcp_timestamps` | `1` | TCP 时间戳选项 | 保持 `1` | ⚠️ 不只是"计时"：PAWS 防回绕、RTT 精测、`tcp_tw_reuse` 的安全前提都依赖它 |
| `net.ipv4.tcp_sack` | `1` | 选择性确认 | 保持 `1` | ⚠️ 关闭会让丢包时重传量大幅增加 |

### 5.5 软中断与 NAPI 预算

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.core.netdev_max_backlog` | `1000` | **每 CPU** 的 softnet backlog 长度上限 | 调大抗收包突发 | ⚠️ **只在走 backlog 的路径生效**（见 2.1）。调大不能解决 CPU 处理能力不足，只是把丢包从"队列满"推迟到"内存压力"。**注意是 per-CPU** |
| `net.core.netdev_budget` | `300` | 一次 `net_rx_action` 最多处理多少报文 | 调大减少 `time_squeeze`，但**增加单次软中断占用 CPU 时间**（恶化延迟） | ⚠️ 典型的"吞吐 vs 延迟"权衡。调大可能造成用户态进程调度抖动。安全范围约 300–600 |
| `net.core.netdev_budget_usecs` | `8000` | 一次 `net_rx_action` 最多占用微秒数 | 同上 | ⚠️ 与 `netdev_budget` 是"先到者生效"的**或**关系，只调一个可能无效 |
| `net.core.dev_weight` | `64` | 每次 NAPI poll 从驱动 ring 取多少包 | 调大减少轮询开销 | ⚠️ 与 `netdev_budget` 是**不同层级**，不要混淆 |
| `net.core.busy_poll` | `0` | `poll()`/`epoll_wait()` 忙等微秒数 | 非 0 降低延迟但**空转烧 CPU** | ⚠️ 仅高 PPS 低延迟场景（如金融行情）有收益；需网卡/驱动支持（`SO_BUSY_POLL`） |
| `net.core.busy_read` | `0` | `read()`/`recv()` 忙等微秒数 | 同上 | ⚠️ 同 `busy_poll`，是"用 CPU 换延迟"的开关 |

### 5.6 安全、过滤与转发

| 参数 | 本机实测 | 作用 | 调大 / 调小 | 风险与常见误用 |
|---|---|---|---|---|
| `net.ipv4.conf.all.rp_filter` | `0` | 反向路径过滤：校验入包源地址的返回路径是否走同接口。`0`关、`1`严格、`2`宽松 | `1` 防 IP 欺骗最有效 | ⚠️ **本机 `all=0` 但 `default=2`**——注意 `all`/`default`/`conf/<iface>` 三者生效规则：实际取 `max(all, iface)`（数值大者优先）。k8s/Calico 常需关闭，否则跨节点 Pod 通信被丢 |
| `net.ipv4.ip_forward` | `1` | 是否允许 IPv4 转发 | `1` 当路由器用 | ⚠️ 本机为 `1`（很可能装了 Docker）。开启转发会让主机变路由器，配合 `rp_filter`/防火墙不当会有安全问题；容器环境通常必须开 |
| `net.ipv4.icmp_echo_ignore_broadcasts` | `1` | 忽略广播 ICMP echo（Smurf 防护） | 保持 `1` | ⚠️ 关闭会让主机参与 Smurf 放大攻击，几乎没有正当理由关闭 |
| `net.ipv4.conf.all.accept_redirects` | `0` | 是否接受 ICMP 重定向（改路由表） | 保持 `0` | ⚠️ 开启会让攻击者能篡改路由表；仅主机本身是网络设备且明确需要时才开 |

> 本表共 **40 项**参数（5.1 连接队列 4 项、5.2 端口与 TIME-WAIT 5 项、5.3 缓冲区 10 项、5.4 拥塞控制与 qdisc 11 项、5.5 软中断 6 项、5.6 安全与转发 4 项）。每项都写了作用、调整方向与风险/常见误用；读法见 5.0。

## 6. 丢包与延迟定位实战

> 每 case 格式：**症状 → 观测 → 判据 → 处置**。所有计数器名都从**本机实测的** `/proc/net/netstat`、`/proc/net/snmp` 表头核对过，不是抄博客。

### case 1：网卡 ring buffer 溢出（驱动层丢包）

**症状**：高 PPS 下丢包，`ss` 看起来正常，抓包也看不到（包在驱动就被丢了）。

**观测**：`ethtool -S <iface> | grep -iE 'miss|drop|no_buffer|fifo|overrun'`；`ethtool -g <iface>` 看 ring 大小；无 root 时读 `/sys/class/net/<iface>/statistics/{rx_missed_errors,rx_fifo_errors,rx_dropped}`。

**判据**：`rx_missed_errors` / `rx_fifo_errors` **持续增长** → ring buffer 溢出（驱动看见包但环里没空位）。⚠️ 各驱动的 `ethtool -S` 计数器名字不同（`rx_no_buffer_count`、`rx_over_errors` 等），**必须看你的驱动实际有哪些**。⚠️ 本机实测 `rx_missed_errors` 是 `n/a`——很多虚拟网卡（virtio、veth）就不上报它，**"看不到"不等于"没有"**。

**处置**：`ethtool -G <iface> rx 4096 tx 4096`（临时）。但**根本解法不是调大 ring**——ring 只能缓冲，真正瓶颈是"内核取包速度跟不上网卡"。应配合：多队列 + RPS/RFS（`/sys/class/net/*/queues/rx-0/rps_cpus`）、提高 `netdev_budget`/`dev_weight`、GRO/GSO、XDP 或 `SO_BUSY_POLL`。

### case 2：softnet backlog 满（软中断来不及处理）

**症状**：丢包，`TcpExt TCPBacklogDrop` 或 `softnet_stat` 第 2 列增长。

**观测**：`cat /proc/net/softnet_stat`（第 2 列 dropped、第 3 列 time_squeeze，**十六进制**）；逐 CPU 看：`awk '{print "CPU"NR-1": dropped=0x"$2" ts=0x"$3}' /proc/net/softnet_stat`；`cat /proc/softirqs` 看 `NET_RX` 在各 CPU 的分布。本机实测第 2、3 列全为 0（无 backlog 丢包）。

**判据**：第 2 列 > 0 且持续增长 → backlog 满。**关键是要看 per-CPU**：只有 CPU0 增长 → **单核瓶颈**（中断/RPS 未均衡）；所有核都丢 → 整体处理能力不足。两者解法完全不同。

> ⚠️ **避免最常见的误判**：第 2 列**只在走 `enqueue_to_backlog()` 时才增长**。现代多队列网卡 + NAPI 直接走 `netif_receive_skb()`，**不经过 backlog**。所以第 2 列全 0 **不能**推出"软中断没瓶颈"——要看第 3 列 `time_squeeze`、`/proc/softirqs` 的 `NET_RX` 增长速率、以及 `ksoftirqd/N` 的 CPU 占用。

**处置**：先确认是否单核瓶颈（`/proc/softirqs`）；治标 `netdev_max_backlog=5000`、`netdev_budget=600`、`netdev_budget_usecs=16000`；治本是 RPS（`echo f > .../rx-0/rps_cpus`）、多队列、中断亲和（`/proc/irq/<n>/smp_affinity`）、XDP。改完**再采样做差验证**。

### case 3：socket 接收队列满（应用读取太慢）

**症状**：没有网络丢包迹象，但应用偶发超时/数据缺失；`Recv-Q` 持续不为 0。

**观测**：`ss -tni | awk 'NR==1 || $2>0'`；`TcpExt TCPRcvQDrop`；`ss -tmi` 看 `skmem` 的 `d`(`sock_drop`) 与 `rb`；`awk 'NR>1 && $5!="00000000" {print $2,$5}' /proc/net/tcp`（`rx_queue` 十六进制）。

**判据**：某条连接 **`Recv-Q` 长期 > 0 且持续增长** → 数据已到 socket 队列但应用没来得及 `read()`，**这是"应用读取慢"的直接证据**。`TCPRcvQDrop` 增长 → 接收队列满导致内核丢包（丢在 socket 队列层，不在网络层）。`skmem` 的 `d>0` → 该 socket 丢过包；`rb` 贴近 `rmem_max` → 缓冲已到上限。

**处置**（**按优先级，不要一上来调内核参数**）：① **先看应用**——是不是 `read()` 太慢或在处理里做了耗时操作（写日志、同步 IO、锁竞争）？调大缓冲只是把"丢包"换成"更高延迟"，不一定更好。② 确需更大缓冲：`sysctl -w net.core.rmem_max=16777216`，**且应用必须显式 `setsockopt(SO_RCVBUF)`**（否则无效）。③ 检查 `tcp_moderate_rcvbuf` 是否为 1。④ 考虑 `SO_RCVLOWAT`、epoll 边缘触发减少唤醒，或多线程分担读取（注意惊群）。

### case 4：conntrack 表满

**症状**：`dmesg` 出现 `nf_conntrack: table full, dropping packet`；大量连接失败但网络本身正常；NAT 环境（Docker/K8s/防火墙）高发。

**观测**：`cat /proc/sys/net/netfilter/nf_conntrack_count` 与 `nf_conntrack_max`；`conntrack -C`（当前条目）、`conntrack -S`（统计，含 `insert_failed`/`drop`）；`cat /proc/net/nf_conntrack | head`；`dmesg | grep -i 'conntrack.*table full'`。

**判据**：`count` 接近 `max` → 快满；`conntrack -S` 的 `insert_failed`/`drop` 增长 → **已在丢包**；`dmesg` 有 `table full` → 确诊。

**处置**：`sysctl -w net.netfilter.nf_conntrack_max=1048576`（治标，注意内存线性增长）；缩短超时：`nf_conntrack_tcp_timeout_established=3600`（默认常为 5 天，连接多但空闲的场景极占表空间）、`nf_conntrack_tcp_timeout_time_wait=30`。⚠️ 该参数只在 `nf_conntrack` 模块加载时可用，否则报 `unknown key`。**更根本的方向**是用 `NOTRACK` 规则绕过不需要跟踪的流量，或用 eBPF（Cilium）替代 iptables/conntrack。

### case 5：TIME-WAIT 端口耗尽（`Cannot assign requested address`）

**症状**：客户端大量报 `EADDRNOTAVAIL`；`ss -s` 里 TIME-WAIT 上万。本机实测 `ss -s`：`TCP: 526 (estab 489, closed 16, orphaned 3, timewait 15)`——数量很小，属健康状态。

**观测**：`ss -tan state time-wait | wc -l`；`TcpExt` 的 `TW`/`TWRecycled`/`TCPTimeWaitOverflow`（本机实测 TW=2598、TWRecycled=0、TCPTimeWaitOverflow=0）；`cat /proc/sys/net/ipv4/ip_local_port_range`。

**判据**：TIME-WAIT 数万 + 客户端 `EADDRNOTAVAIL` → 端口耗尽。关键公式：**可用端口数 = `ip_local_port_range` 跨度**（本机 `32768 60999` = 28231 个）。若这些端口都被 TIME-WAIT 占着（默认各 60 秒），QPS 上限约 `28231/60 ≈ 470 连接/秒`（粗略估算）。`TCPTimeWaitOverflow` 增长 → 达到 `tcp_max_tw_buckets`，内核强制销毁 TIME-WAIT，**破坏了协议保护**。

**处置**：① 扩大端口范围 `sysctl -w net.ipv4.ip_local_port_range="10000 65535"`；② `sysctl -w net.ipv4.tcp_tw_reuse=1`（本机实测 2；**各取值精确语义以 6.12 源码 `net/ipv4/tcp_ipv4.c` 中判断该参数的分支为准**）；③ **不要做**：不要改 `tcp_fin_timeout` 来"缩短 TIME-WAIT"（它管 FIN_WAIT2）；不要调小 `tcp_max_tw_buckets`；**不要设 `tcp_tw_recycle`——该参数在 Linux 4.12 已被移除**，网上"调它解决 TIME-WAIT"的文章已过期且在 NAT 下会导致连接随机失败（本机 `sysctl` 里确实没有它）。**根本方向**：TIME-WAIT 堆积的本质是**短连接太多**，改成连接池/长连接比调任何参数都有效。

### case 6：TCP 重传与 RTO 误判（延迟类问题的经典陷阱）

**症状**：延迟高、P99 抖动，`RetransSegs`/`TCPTimeouts` 看起来很高，于是判断"网络丢包严重"。

**观测**：`grep '^Tcp:' /proc/net/snmp`（本机实测 `OutSegs=18964484`、`RetransSegs=2813` → 重传率 `2813/18964484 ≈ 0.0148%`，**远低于 1%，完全正常**）；`TcpExt` 的 `TCPTimeouts`/`TCPLostRetransmit`/`TCPOFOQueue`（本机实测 2112 / 1738 / 83984）；`ss -tni | grep -E 'rtt|retrans|cwnd|unacked|app_limited'`。

**判据（必须一起看多个指标）**：

| 现象 | 真相 |
|---|---|
| 重传率 **< 1%** | **正常**。公网 0.1%–1% 是常态，不要据此断定网络有问题 |
| `TCPTimeouts` 高但 `TCPLostRetransmit` 低 | 多是**超时重传**（RTO 偏小或对端 ACK 延迟），**不一定**是丢包 |
| `TCPLostRetransmit` **高** | 重传的包**又丢了** → 真正的严重丢包/拥塞 |
| `ss -tni` 出现 `app_limited` | 发送受限于**应用**而非网络 → **别调网络参数** |
| `rtt` 小而 `retrans` 大 | 可能是**接收端**问题（延迟 ACK、缓冲不足） |
| 所有连接 `unacked` ≈ `cwnd` 且 `cwnd` 小 | 发送被拥塞窗口卡住 → 真实丢包或 RTT 很大 |
| `TCPOFOQueue` 高但重传率低 | **乱序**而非丢包（多路径/负载均衡），TCP 能处理，通常无需处理 |

**处置**：① **先算重传率**，别被绝对值吓到；② 区分乱序与丢包（`TCPOFOQueue` 高 + 重传率低 = 乱序）；③ 看 `app_limited`，有则瓶颈在应用；④ 确认真实丢包后，再沿第 1 节漏斗向下查（ring → backlog → socket）；⑤ 只有确认"不是丢包而是缓冲不足"时才考虑调 `tcp_rmem`/`tcp_wmem` 或换拥塞算法。

> ⚠️ **RTO 的常见误判**：RTO 最小值受 `TCP_RTO_MIN`（通常 200ms）限制，`ss -tni` 显示的 `rto:` 就是当前计算值，本机实测 `rto:204` 是**正常**的。RTO 在连续超时后**指数退避翻倍**，所以重传时 `rto` 变大是**结果**不是原因。

### case 7：SYN 队列溢出（服务端"连不上"）

**症状**：客户端连接超时/被拒；服务端负载不高但新连接建立困难；可能伴随 SYN Flood 或连接突发。

**观测**：`TcpExt` 的 `ListenOverflows`/`ListenDrops`/`TCPReqQFullDrop`/`TCPReqQFullDoCookies`/`SyncookiesSent`/`EmbryonicRsts`；`ss -tan state syn-recv | wc -l`；`ss -lnt | awk 'NR>1 && $2>0'`；以及 `somaxconn`/`tcp_max_syn_backlog`/`tcp_syncookies`。

**本机实测 `ListenOverflows = ListenDrops = 58`** —— 说明这台机器上**确实发生过 58 次 accept 队列溢出**。虽然当前 `ss -lnt` 显示队列无积压（Send-Q 都是 0），但历史计数器记录了下来。**这正是"累计计数器"的价值**：它记录了瞬时观测抓不到的偶发事件。

**判据**：

| 计数器 | 含义 |
|---|---|
| `ListenOverflows` | **全连接队列**溢出：三次握手已完成但应用没 `accept()`，队列满后新连接被丢 |
| `ListenDrops` | 因 listen 队列满而丢弃的 SYN |
| `TCPReqQFullDrop` | **半连接队列**满且 `tcp_syncookies=0`，丢弃 SYN |
| `TCPReqQFullDoCookies` | 半连接队列满但启用 syncookies，用 cookie 顶住（**没丢包**） |
| `SyncookiesSent` | 发出的 SYN cookie 数 |
| `EmbryonicRsts` | 收到对"已不存在的半连接"的 ACK，说明握手有异常 |

**处置**：① 全连接队列溢出 → `sysctl -w net.core.somaxconn=8192`，**且必须同时改应用的 `listen()` backlog**（内核取 `min(somaxconn, backlog)`，只改一边无效）：Nginx `listen ... backlog=8192;`、Redis `tcp-backlog 8192`、Netty 设 `SO_BACKLOG`。② 半连接队列溢出 → `tcp_max_syn_backlog=8192` + `tcp_syncookies=1`（本机已是 1）。

> ⚠️ **两个关键区分**：① **`ListenOverflows` 是"应用 accept 慢"，不是"内核处理不过来"**——解法是让应用更快 `accept()` 或调大 backlog，**而不是**调软中断参数。这是最常见的方向性误判。② **只有 `TCPReqQFullDrop` 才是真的丢 SYN**；若涨的是 `TCPReqQFullDoCookies`，说明 syncookies 生效、握手**没有失败**，此时是"预警"而非"故障"。

### 6.8 性能反模式清单（比调参数更重要）

内核参数能解决的性能问题其实**很少**。下面这些更常见，且**调任何 `sysctl` 都救不了**：

| # | 反模式 | 为什么坏 | 正确做法 |
|---|---|---|---|
| 1 | **每连接一线程** | 线程栈开销（默认 8MB 虚拟内存/线程）、上下文切换，无法支撑 C10K+ | `epoll` + 事件循环；或用固定数量线程池 |
| 2 | **用户态多余拷贝** | 每次 `read()`+`write()` 都有内核↔用户态拷贝，成为 CPU 瓶颈 | `sendfile()`/`splice()`/`mmap()`+`write()`，或 `MSG_ZEROCOPY` |
| 3 | **socket 缓冲区设置错误** | 太小吞吐上不去（BDP 不足）；太大会增加延迟。**只改 `rmem_max` 而应用不 `setsockopt` 完全无效** | 按 BDP = 带宽×RTT 计算；延迟敏感用 `TCP_NOTSENT_LOWAT`，不盲目调大 |
| 4 | **在数据面做日志** | 每请求同步写日志 → IO + 锁竞争，吞吐断崖下跌，是"压测上不去"头号原因 | 异步/采样日志，或用 eBPF 在内核聚合统计（无日志开销） |
| 5 | **滥用 `SO_REUSEPORT` 而不做均衡** | 内核按四元组 hash 分配，hash 不均或 worker 能力不同会出现"忙死/闲着" | 确认 hash 分布；必要时 `SO_ATTACH_REUSEPORT_EBPF` 自定义分发 |
| 6 | **忽略 accept 队列** | 只调 `somaxconn` 不改应用 backlog（取 min）；或 `accept` 后做耗时操作再回来 | 两边一起改；`accept` 后立即把 fd 交给工作线程 |
| 7 | **短连接硬扛** | 每请求建连 → TIME-WAIT 堆积、握手开销、端口耗尽 | 连接池 / keep-alive / HTTP/2 多路复用 |
| 8 | **热路径上做内存分配** | 每包/每请求 `malloc` → 分配器锁竞争、cache 失效 | 对象池、tcmalloc/jemalloc、预分配 |
| 9 | **盲目更换拥塞控制算法** | 换 BBR 不一定更快（可能与 CUBIC 流不公平、与浅缓冲设备冲突） | 先在测试环境对比；注意配 `fq` qdisc 才能发挥 BBR pacing |
| 10 | **只看平均值** | 平均 10ms 可能隐藏着 P99 = 2s 的严重问题 | 永远看分位数（P50/P95/P99/P999），并与 `ss -tni` 的 `rtt` 对照 |
| 11 | **在容器里查宿主机的网络问题** | netns 隔离，看不到宿主机网卡/软中断 | 先明确问题属于哪个 netns（见 4.5） |
| 12 | **用 `tcpdump` 抓全量包做性能分析** | 抓包本身开销巨大（尤其 `-s 0`），把"观测"变成"干扰" | 用计数器/`ss`/eBPF 聚合；必须抓时用 `-c` 限量 + BPF 过滤 + 只抓头部 |

## 7. 小结与延伸阅读

### 7.1 一页纸总结

**方法论**：用**漏斗**（应用 → 汇总 → socket 队列 → TCP 计数器 → 软中断 → 网卡 → tracepoint），**不要跳层**，不要一上来抓包。先分清"丢包"还是"延迟"，二者根因常完全不同。多数计数器是**累计值**，必须采样做差。

**关键结构**：**三个队列**（网卡 ring → softnet backlog → socket 接收队列）分别在驱动层、软中断层、socket 层溢出，各有各的计数器。`/proc/net/*` 全部可读、大多不需 root。`softnet_stat` 是**十六进制、per-CPU、本机 15 列，且列数随内核版本变化**。`sockstat` 的 `mem`、`tcp_mem`/`udp_mem` 单位是**页**。

**观测点**：收包路径上有 ⑩ 个可观测点（第 3.1 节图）。`ListenOverflows` 属于"应用 accept 慢"，**不是**内核处理不过来。`ss -tni` 的 `app_limited` 说明瓶颈在应用。

**工具**：`ss -s/-lntp/-tni/-tm/-to/-e/state/`-K`——`i` 看内核 TCP 变量，`m` 看 `skmem` 九字段，`o` 看定时器。容器里**必须先确定问题属于哪个 netns**；veth 成对统计定位丢包在哪一侧。

**调优三类典型误用**：`tcp_fin_timeout` **不控制 TIME-WAIT**（固定 2MSL）；`somaxconn` 必须和应用 `listen()` backlog 一起改（取 min）；`tcp_fastopen` 是**位掩码**不是布尔值（本机 `1` = 只启用客户端）。`rmem_max`/`wmem_max` 只改内核不够，**应用必须 `setsockopt`**。

**7 个 case 判据速查**：

| case | 一句话判据 |
|---|---|
| 1 ring buffer 溢出 | `rx_missed_errors`/`rx_fifo_errors` 持续增长 |
| 2 softnet backlog 满 | `softnet_stat` 第 2 列增长（**只在走 backlog 路径时才有意义**）；单核 vs 全核要分清 |
| 3 socket 接收队列满 | `ss` 的 `Recv-Q` 持高 + `TCPRcvQDrop` 增长 |
| 4 conntrack 表满 | `nf_conntrack_count` 接近 `max` + dmesg `table full` |
| 5 端口耗尽 | TIME-WAIT 数万 + `EADDRNOTAVAIL`；可用端口数 = 端口范围跨度 |
| 6 重传误判 | 先算**重传率**，再靠 `app_limited`/`TCPLostRetransmit`/`TCPOFOQueue` 区分原因 |
| 7 SYN/accept 队列溢出 | `ListenOverflows`（accept 慢）vs `TCPReqQFullDrop`（真丢 SYN） |

**反模式比参数重要**：每连接一线程、数据面打日志、多余拷贝、短连接硬扛——调什么参数都没用。

> **最后一句话：调参数之前先测量。** 本章 7 个 case 里多数真正的根因不在"内核参数不对"，而在"应用行为不对"（读取慢、accept 慢、短连接太多、数据面打日志）。内核参数是**最后一公里**，不是第一手段。
