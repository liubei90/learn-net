# 第 4 章 网络层：IP 路由与邻居子系统

## 0. 本章定位

**处于协议栈哪一层**：本章覆盖 Linux 网络栈的**网络层（L3）**——
IPv4 的输入、转发、输出，以及为 L3 服务的**路由子系统（FIB）**与
**邻居子系统（ARP/ndisc）**。向上承接传输层，向下依赖链路层。

**前置章节**：`docs/01`（socket API 入口）、`docs/03`（netlink 配置通道，见 `labs/03`）。


**学完能回答什么问题**：
1. 一个目的地址非本机的包，从 `ip_rcv` 进来到 `ip_forward` 出去，中间经过哪些函数？
2. 本机地址的判定发生在哪里？为什么 `ip route` 里会有一张 `local` 表？
3. 为什么 4.18 要删掉路由缓存（rtable cache）？删了之后靠什么加速查找？
4. `skb->dst`（`dst_entry`）到底缓存了什么？`rtable` 与 `dst_entry` 是什么关系？

6. netfilter 的 5 个 hook 分别在 L3 路径的哪个位置？分片、PMTU、
   ICMP 差错、RP filter、策略路由各解决什么问题？

## 1. 核心概念与设计权衡

### 1.1 网络层的三件事

Linux 的 IPv4 层只做三件事，但每件都很讲究：

1. **决定去向（路由决策）**：查 FIB（Forwarding Information Base）得到
   「从哪个设备出、下一跳是谁、源地址选哪个、用什么 type 处理」。
2. **决定丢不丢（策略/校验）**：RP filter、netfilter、路由 type
   （`RTN_UNREACHABLE`/`RTN_THROW`/`RTN_BLACKHOLE`）都在这一步把关。
3. **把包送出去或交给上层（投递）**：本地投递（`ip_local_deliver`）、
   转发（`ip_forward`）、或 L2 解析后发出（`neigh_output`）。

### 1.2 设计权衡：路由缓存为什么必须被删掉

Linux 4.18 之前有一个 **rtable cache（路由缓存）**：每个流（或每个
目的地址）第一次查 FIB 后，把结果 `struct rtable` 缓存起来，后续同目的
地址的包直接命中缓存，O(1)。

它被删除（4.18，Eric Dumazet 的重构）的原因是：

| 问题 | 说明 |
|---|---|
| 可扩展性差 | 缓存是全局共享、随流数量增长的数据结构；DDoS 场景下大量随机目的地址会让缓存剧烈颠簸（cache thrash），反而比直接查表更慢，还带来内存与锁竞争压力 |
| 一致性问题 | 路由变更（`ip route`、网卡 down）时必须**逐条失效**缓存，容易漏、容易产生"路由已改但旧流还在走老路"的困惑 |

**结论**：4.18 起，数据面**直接查 FIB trie**；`rtable` 仍然存在，但它
不再是一张"缓存表"，而是**一次路由查找的结果对象**，通常挂在 skb 上
用完即弃，其生命周期远短于以前的 cache 项。

> 一个重要后果：现在"同一个目的地址的两次查找"不保证拿到同一个
> `rtable` 指针。因此**不要**把历史文档里"路由缓存查找/失效"的知识
> 直接套到 5.x/6.x。

### 1.3 设计权衡：为什么 FIB 用压缩前缀树（LC-trie）

- 路由表是**前缀匹配**问题：`10.0.0.0/8` 与 `10.1.0.0/16` 可能同时存在，
  必须取**最长前缀匹配（LPM, Longest Prefix Match）**。
- 哈希表做不到 LPM；线性表是 O(n)。
- **压缩前缀树（Patricia trie / LC-trie）**把「只有一个孩子的链」
  压缩掉（路径压缩），使查找复杂度约为 O(W)，W 为地址位宽（IPv4 为 32，
  实际远小于 32 跳），且内存开销小、支持 RCU 无锁读。

### 1.4 设计权衡：控制面与数据面分离

- **控制面**：`ip route add/del`（netlink `RTM_NEWROUTE`/`RTM_DELROUTE`）、
  路由协议守护进程（bird/frr）、DHCP。它们通过 `inet_rtm_newroute`
  等函数修改 FIB；改动是**低频**的。
- **数据面**：每个包查一次 FIB（`fib_table_lookup`）；是**高频**的。
- 两者通过 RCU 协调：控制面用"构建新节点 + 原子替换指针 + 延迟释放"
  的方式更新，数据面读侧几乎无锁。这是 Linux 能同时做到
  "可以随时改路由"和"转发性能高"的关键。


## 2. 关键内核数据结构（真实 struct 与源码路径）

> 以下字段均核对过 Linux 6.12 源码。凡本章未列出字段细节的结构，
> 请以 6.12 为准，可在 <https://elixir.bootlin.com/linux/v6.12/source/> 核对。

### 2.1 `struct dst_entry` 与 `struct rtable`

`dst_entry` 是**"这个包接下来怎么走"的抽象**，定义在
`include/net/dst.h`。它不是一个具体协议的结构，而是被嵌入到具体
实现里：IPv4 的输入/输出路由就是 `struct rtable`。

```
struct rtable {            // include/net/route.h
        struct dst_entry dst;   // 关键：rtable 的第一个成员就是 dst_entry
        ...
};
```

**这层"嵌入 + 首成员"的关系非常重要**：因为 `dst` 是第一个成员，
`struct rtable *` 与 `struct dst_entry *` 可以互相强转，这是全内核
`skb_dst()`、`dst_output()` 能对 IPv4/IPv6/其他地址族统一处理的原因。

`dst_entry` 里与数据面直接相关的成员（概念层面）：

| 成员（概念） | 作用 |
|---|---|
| `input` / `output` | 函数指针。`input` 决定**收到包后往哪走**（本地投递 or 转发）；`output` 负责**发送前处理**（分片、邻居解析等） |
| `dev` | 出口（或入口）网络设备 |
| `ops` | 一组操作（`struct dst_ops`），含 `link_failure`、`update_pmtu`、`redirect`、`neigh_lookup` 等 |
| `obsolete` / `flags` | 失效标记与标志位。6.12 `include/net/dst.h` 实测可用值：`DST_OBSOLETE_*`、`DST_NOCOUNT`、`DST_NOXFRM`、`DST_NOPOLICY`、`DST_FAKE_RTABLE`、`DST_XFRM_*`、`DST_METADATA`（老资料里的 `DST_HOST`、`DST_NOCACHE` **已被删除**，不要照抄） |
| `__metrics` | MTU / RTT / 窗口等度量值 |

`skb->dst`（`skb->_skb_refdst` 里保存的指针）的作用就是：
**把"这次路由查找的结果"随包携带**，避免在同一个包的后续处理中
重复查 FIB，同时让分片、邻居解析、PMTU 等下游代码能拿到
出口设备、MTU、下一个 `dst`（用于隧道嵌套）。

`struct rtable` 中还有一个容易忽略的细节：
`struct rtable`（`include/net/route.h`）里有 `__u8 rt_uses_gateway` **字段**（不是宏），用于判断这条路由
是否经由网关（即是否需要 ARP 解析下一跳，而不是目的地址本身）。

### 2.2 FIB 的核心结构（`include/net/ip_fib.h`）

FIB 的设计是**三层**的，理解这三层是理解本章的关键：

```
struct fib_table {           // 一张路由表（如 main / local / 自定义表）
        struct hlist_node tb_hlist;
        u32               tb_id;          // 表 id：RT_TABLE_MAIN=254, LOCAL=255...
        int               tb_num_default;
        struct rcu_head   rcu;
        unsigned long     *tb_data;       // 指向 net/ipv4/fib_trie.c 里的 struct trie
        unsigned long     __data[];
};
```

> 注意 `tb_data` 的类型是 `unsigned long *`，但实际指向的是
> `struct trie`（`fib_trie.c` 里用 `struct trie *t = (struct trie *)tb->tb_data;`
> 取回）。这是一种"类型擦除"手法，目的是让 FIB 的对外结构
> （`include/net/ip_fib.h`）不暴露 trie 的内部实现。

```
struct fib_info {            // 一组「下一跳 + 公共属性」，多个 fib_alias 可共享它
        struct hlist_node fib_hash, fib_lhash;
        refcount_t        fib_treeref, fib_clntref;
        unsigned char     fib_dead, fib_protocol, fib_scope, fib_type;
        __be32            fib_prefsrc;
        u32               fib_tb_id, fib_priority;
        struct dst_metrics *fib_metrics;
        int               fib_nhs;        // 下一跳个数（ECMP 多路径）
        struct fib_nh     fib_nh[] __counted_by(fib_nhs);   // 柔性数组
        /* 还有 fib_flags/fib_net/nh 等，见 include/net/ip_fib.h */
};
```

`fib_info` 上的几个宏值得记住（它们说明 MTU/RTT/窗口是从 metrics 数组
**按索引**取的）：

```c
#define fib_mtu    fib_metrics->metrics[RTAX_MTU-1]
#define fib_window fib_metrics->metrics[RTAX_WINDOW-1]
#define fib_rtt    fib_metrics->metrics[RTAX_RTT-1]
#define fib_advmss fib_metrics->metrics[RTAX_ADVMSS-1]
```

```
struct fib_nh_common {       // v4/v6 共用的下一跳部分（6.x 的重构成果）
        struct net_device *nhc_dev;
        int               nhc_oif;
        unsigned char     nhc_scope, nhc_flags;
        u8                nhc_family, nhc_gw_family;
        struct lwtunnel_state *nhc_lwtstate;      // 轻量隧道（如 MPLS/seg6）
        union { __be32 ipv4; struct in6_addr ipv6; } nhc_gw;
        int               nhc_weight;             // 多路径权重
        struct rtable __rcu * __percpu *nhc_pcpu_rth_output;
        struct rtable __rcu           *nhc_rth_input;
        struct fnhe_hash_bucket __rcu *nhc_exceptions;   // PMTU/redirect 例外（fnhe）
};
```

```
struct fib_nh {              // IPv4 的下一跳 = 公共部分 + v4 专有字段
        struct fib_nh_common nh_common;
        struct fib_info     *nh_parent;
        __be32               nh_saddr;        // 该下一跳优选出的源地址（缓存）
        int                  nh_saddr_genid;
};
```

`fib_nh` 刻意用一组宏把公共字段"投影"出来（如
`#define fib_nh_dev nh_common.nhc_dev`、`fib_nh_gw4` → `nhc_gw.ipv4`），
这样代码里既有 v4 的直观命名，又不必重复定义字段。

**路由条目（叶子）**：`struct fib_alias` 定义在
**`net/ipv4/fib_lookup.h`**（注意不是 `include/net/ip_fib.h`）：

```
struct fib_alias {
        struct hlist_node fa_list;
        struct fib_info  *fa_info;      // 指向共享的 fib_info
        dscp_t            fa_dscp;
        u8                fa_type;      // RTN_UNICAST / RTN_LOCAL / ...
        u8                fa_state;
        u8                fa_slen;
        u32               tb_id;
        s16               fa_default;
        u8                offload, trap, offload_failed;
        struct rcu_head   rcu;
};
```

**为什么要有 `fib_alias` 这一层**：同一个前缀可能同时存在多条路由
（不同 TOS/DSCP、不同 type），它们**共享**同一个 `fib_info`
（同样的下一跳集合）。这样 `ip route` 加 1000 条同下一跳的路由，
只存一份 `fib_info`。`fa_type` 决定了命中后是 `RTN_LOCAL` 还是
`RTN_UNICAST` 等 —— 这就是"路由类型"的落点。

`net/ipv4/fib_lookup.h` 里还定义了 `struct fib_prop` 与
`extern const struct fib_prop fib_props[RTN_MAX + 1];`：
**每种 RTN 类型对应的默认 scope 与 error**，是"路由类型"语义的表格化表达。

### 2.3 FIB trie 的真实节点结构（`net/ipv4/fib_trie.c`）

这是本章最值得精读的结构：

```c
struct key_vector {
        t_key key;               // 本节点覆盖的前缀位
        unsigned char pos;       // 2log(KEYLENGTH) bits needed
        unsigned char bits;      // 2log(KEYLENGTH) bits needed
        unsigned char slen;
        union {
                /* This list pointer if valid if (pos | bits) == 0 (LEAF) */
                struct hlist_head leaf;
                /* This array is valid if (pos | bits) > 0 (TNODE) */
                DECLARE_FLEX_ARRAY(struct key_vector __rcu *, tnode);
        };
};
```

**源码注释直接给出了判别规则**：`(pos | bits) == 0` 时是
**叶子（LEAF）**，`union` 里的 `leaf` 是挂 `fib_alias` 链的
`hlist_head`；否则是**内部节点（TNODE）**，`tnode` 是按位索引子节点的
柔性数组。内部节点是：

```c
struct tnode {
        struct rcu_head rcu;
        t_key empty_children;    // 位图：哪些孩子为空
        t_key full_children;     // 位图：哪些孩子是满子树
        struct key_vector __rcu *parent;
        struct key_vector kv[1];
#define tn_bits kv[0].bits
};
```

要点：
- **内部节点（tnode）与叶子共用 `struct key_vector` 头部**，因此
  `leaf_walk_rcu` 等遍历代码可以对两者统一处理。
- `empty_children`/`full_children` 是**位图**，供 `fib_insert_alias`
  在插入/删除时快速判断是否合并或分裂节点。
- `__rcu` 标注说明子节点指针受 RCU 保护，读侧无需加锁。

> ⚠️ **准确性更正（重要）**：很多老教程（以及一些课程提纲）会提到
> `struct fib_node`。**在 Linux 6.12 中并不存在 `struct fib_node`** ——
> 它是早已被移除的 `fib_hash` 实现的遗留物。当前 trie 实现里承担
> "节点"角色的是 `struct key_vector`、`struct tnode`，以及叶子上的
> `struct fib_alias` 链。请勿再引用 `fib_node`。

**查找函数签名（注意返回类型是 `int`）**：

```c
int fib_table_lookup(struct fib_table *tb, const struct flowi4 *flp,
                     struct fib_result *res, int fib_flags);   // net/ipv4/fib_trie.c
```

它在失败时返回负的 errno，并在成功时填充 `struct fib_result`
（定义在 `include/net/ip_fib.h`，含 `fi`/`nhc`/`type`/`prefixlen`/`table`
等；`FIB_RES_DEV` 等宏用于取出口设备）。失败路径上会调用
`trace_fib_table_lookup(...)`（`net/ipv4/fib_trie.c` 里多次出现），
这是一个可用于观测的 tracepoint。

相关函数：`fib_find_node`（按 key 定位节点）、`fib_insert_alias`（插入
路由条目）、`leaf_walk_rcu`（遍历叶子）、`fib_table_lookup`（查找）。

输入侧的路由查找封装在 `net/ipv4/route.c`：`ip_route_input_noref` →
`ip_route_input_rcu` → `ip_route_input_slow`（内部用 `__mkroute_input`
和 `rt_dst_alloc` 构造 `struct rtable`）；输出侧入口是
`ip_route_output_flow`。

### 2.4 策略路由：`struct fib_rule`（`include/net/fib_rules.h`）

```c
struct fib_rule {
        struct list_head list;
        int              iifindex, oifindex;
        u32              mark, mark_mask, flags, table;
        u8               action;      // FR_ACT_TO_TBL / FR_ACT_UNREACHABLE ...
        u32              pref;        // 优先级：越小越先匹配（= ip rule 的 pref）
        int              suppress_ifgroup, suppress_prefixlen;
        char             iifname[IFNAMSIZ], oifname[IFNAMSIZ];
        struct fib_kuid_range uid_range;
        struct fib_rule_port_range sport_range, dport_range;   // 可按端口匹配
        struct rcu_head  rcu;
};
```

`ip rule` 的输出正是这个结构：`pref` 就是 `ip rule` 里的数字，
`table` 就是 `lookup <table>`，`action` 表示"去查表"还是"直接拒绝"。
匹配/动作逻辑在 `net/ipv4/fib_rules.c`
（`fib4_rule_match`、`fib4_rule_action`、`fib4_rule_configure`），
通用框架在 `net/core/fib_rules.c`（`fib_rules_lookup`、`fib_nl_newrule`、
`fib_rules_register`、`fib_rules_event`）。

### 2.5 邻居子系统：`include/net/neighbour.h` + `net/core/neighbour.c`

```
struct neigh_table { ... }     // 一张邻居表（ARP、ndisc、邻居发现的实例）
struct neighbour { ... }       // 一个邻居条目（"这个 IP 的 MAC 是什么"）
struct pneigh_entry { ... }    // 代理 ARP 条目（proxy_arp 用）
struct neigh_ops { ... }       // 按 NUD 状态切换的一组操作
```

> ⚠️ **准确性更正**：不存在 `struct neigh_entry`。邻居表里的条目类型
> 就叫 **`struct neighbour`**；代理（proxy）条目是 `struct pneigh_entry`。ARP 的入口是 `arp_rcv` → `arp_process`（`net/ipv4/arp.c`），需要时经 `neigh_update` 更新邻居表；主机主动通告自身地址即发送**免费 ARP（gratuitous ARP）**。

`neigh_output()` 是一个**内联函数**（在 `include/net/neighbour.h` 里），
它是 L3 走到 L2 的必经之路：

```
neigh_output(neigh, skb, ...)
   ├── 若邻居可用（NUD_CONNECTED：REACHABLE/DELAY/PROBE/PERMANENT/NOARP）
   │      -> neigh_connected_output()（直接填好 L2 头发出）
   └── 否则 -> neigh->output 即 neigh_resolve_output()
          -> 触发/等待 ARP 解析（__neigh_event_send / neigh_event_send）
```

`net/core/neighbour.c` 中的关键函数：
`__neigh_create`、`neigh_lookup`、`neigh_update`、`neigh_resolve_output`、
`neigh_event_send`、`__neigh_event_send`、`neigh_timer_handler`（状态机核心）、
`neigh_periodic_work`（周期回收/老化）、`neigh_forced_gc`、
`neigh_probe`（状态探测）、`neigh_alloc`、`neigh_destroy`、`neigh_ifdown`、
`pneigh_lookup`。

### 2.6 NUD 状态机

状态常量（`include/uapi/linux/neighbour.h`，实测数值）：

| 常量 | 值 | 含义 |
|---|---|---|
| `NUD_INCOMPLETE` | 1 | 正在解析（ARP 已发出，等应答），包被排队 |
| `NUD_REACHABLE` | 2 | 确认可达，可放心使用 |
| `NUD_STALE` | 4 | 已过确认期但**仍可直接使用**，同时后台重新确认 |
| `NUD_DELAY` | 8 | 刚过期，先延迟再用（给上层机会确认） |
| `NUD_PROBE` | 16 | 正在主动探测 |
| `NUD_FAILED` | 32 | 解析失败，包被丢弃 |
| `NUD_NOARP` / `NUD_PERMANENT` | 64 / 128 | 无需 ARP（loopback/点对点/隧道）/ 静态永不老化 |

状态迁移（结合 `neigh_timer_handler`）：

```
   需要发但不知道 MAC            收到 ARP reply
   (无条目) ──► NUD_INCOMPLETE ──► NUD_REACHABLE ──(reachable_time 到期)──► NUD_STALE
                    │                  ▲                                      │
                    │探测用尽          │收到确认                     (有包要发) │
                    ▼                  │                                      ▼
               NUD_FAILED         NUD_PROBE ◄──(delay 到期)──────────── NUD_DELAY
```

设计要点：
- **`NUD_STALE` 仍可直接发包**（这就是 ARP 的"乐观"之处）：不阻塞数据面，
  同时后台重新确认。只有 `INCOMPLETE` 才会把包**排队**。
- `NUD_DELAY` 是"给上层一个机会"：如果上层（如 TCP）在 delay 期间
  用这条邻居发了数据并得到确认，就无需真的发 ARP 探测。
- `NUD_NOARP` 让 loopback、点对点、TUN 等设备完全跳过 L2 解析。

## 3. 数据流与函数调用链

### 3.1 接收路径（RX）

```
网卡驱动 RX 中断 -> NAPI -> napi_gro_receive -> netif_receive_skb
   └─► __netif_receive_skb_core              (net/core/dev.c)
         ├─► AF_PACKET: packet_rcv/tpacket_rcv        ← labs/04 在这里旁路
         └─► ip_rcv                          (net/ipv4/ip_input.c) ← L3 入口
               └─► ip_rcv_core               检查长度/版本/校验和/分片
                     └─► ip_rcv_finish -> ip_rcv_finish_core
                           ├─ 若 skb 无 dst：ip_route_input_noref
                           │    -> ip_route_input_rcu -> ip_route_input_slow
                           │         -> fib_lookup / fib_table_lookup
                           └─► dst_input(skb)  即 skb_dst(skb)->input(skb)
                                 ├─► ip_local_deliver   （本地投递）
                                 └─► ip_forward         （转发）
```

本地投递：

```
ip_local_deliver
   ├─► 若是分片：ip_defrag() 先重组
   └─► ip_local_deliver_finish -> ip_protocol_deliver_rcu
         ├─► raw_local_deliver(skb, protocol)   ← 先投给 RAW socket（labs/04 相关）
         └─► inet_protos[protocol]->handler     ← icmp_rcv / tcp_v4_rcv / udp_rcv
```

转发：

```
ip_forward
   ├─► 检查 TTL（<=1 则 icmp_send 发 Time Exceeded 并丢弃）
   ├─► ip_decrease_ttl / 处理 IP 选项
   └─► ip_forward_finish
         └─► dst_output(skb)     （即 skb_dst(skb)->output(skb) == ip_output）
```

### 3.2 发送路径（TX）

```
传输层
  ├─ TCP: tcp_transmit_skb -> ip_queue_xmit      (net/ipv4/ip_output.c)
  └─ UDP: udp_send_skb     -> ip_send_skb        (net/ipv4/ip_output.c)
        │
        └─► __ip_local_out                       构造/校验 IP 首部、算校验和
              └─► nf_hook(NF_INET_LOCAL_OUT)     ← netfilter hook #4
                    └─► dst_output(skb)
                          └─► ip_output          设置 skb->dev、处理 IP 选项
                                └─► ip_finish_output
                                      ├─► 超过 MTU 且需要分片 -> ip_do_fragment / ip_fragment
                                      ├─► GSO 场景 -> ip_finish_output_gso
                                      └─► ip_finish_output2
                                            └─► neigh_output   (include/net/neighbour.h)
                                                  ├─► neigh_connected_output  （已知 MAC）
                                                  └─► neigh_resolve_output    （触发 ARP）
```

转发出去的包走的是另一条输出链（`ip_forward_finish` -> `dst_output`
-> `ip_output`），并在途中经过 `NF_INET_FORWARD` 与
`NF_INET_POST_ROUTING` 两个 hook。

### 3.3 netfilter 在 L3 的 5 个 hook

```
                 ┌──────────────────────── 本机进程 ────────────────────────┐
                 │                                                        │
                 ▼                                                        ▲
        [LOCAL_OUT #4]                                            [LOCAL_IN #2]
                 ▲                                                        │
                 │                                                        │
   (发送) ──► 路由决策 ──► [POST_ROUTING #5] ──► 出设备            路由决策 ◄── [PRE_ROUTING #1] ◄── 入设备
                 ▲                                                        │
                 │                                                        ▼
                 └────────────► [FORWARD #3] ◄────────────────────────────┘
                            （仅转发，不经过本机进程的包）
```

| # | hook | 宏常量 | 位置 | 典型用途 |
|---|---|---|---|---|
| 1 | PRE_ROUTING | `NF_INET_PRE_ROUTING` | `ip_rcv` 之后、路由决策之前 | DNAT、连接跟踪入口、mangle |
| 2 | LOCAL_IN | `NF_INET_LOCAL_IN` | 路由判定为本地之后、交给传输层之前 | 主机防火墙 INPUT |
| 3 | FORWARD | `NF_INET_FORWARD` | 路由判定为转发之后 | 转发过滤 |
| 4 | LOCAL_OUT | `NF_INET_LOCAL_OUT` | 本机发包、路由决策之前 | OUTPUT 链、DNAT（本机发起） |
| 5 | POST_ROUTING | `NF_INET_POST_ROUTING` | 路由决策之后、真正发出之前 | SNAT/MASQUERADE、mangle |

调用方式统一通过 `NF_HOOK` 宏：它先尝试 `nf_hook()`，若返回
`NF_ACCEPT`（1）就继续执行后面的 `okfn`；否则交给 netfilter 的
继续机制。所以你在源码里看到的形态是：

```c
return NF_HOOK(NFPROTO_IPV4, NF_INET_LOCAL_OUT, net, sk, skb,
               NULL, skb_dst(skb)->dev, dst_output);
```

### 3.4 分片、PMTU 与 ICMP 差错

- **接收侧重组**：`ip_defrag` → `ip_frag_queue` → `ip_frag_reasm`
  （`net/ipv4/ip_fragment.c`），另有 `ip_expire`（重组超时丢弃）、
  `inet_frag_find`（按 (saddr,daddr,id,proto) 找重组队列）。
- **发送侧分片**：`ip_fragment` / `ip_do_fragment`（`net/ipv4/ip_output.c`）。
- **PMTU**：当包过大且设置了 `DF` 位，中间路由器会回
  ICMP Fragmentation Needed；本机据此更新路径 MTU，
  入口是 `ip_rt_update_pmtu`（`net/ipv4/route.c`），
  更新结果记录在下一跳的 **fnhe（next-hop exception）**
  （`nhc_exceptions`，见 `fib_nh_common`）。
- **PMTU 黑洞**：如果中间设备静默丢包而不回 ICMP（常见于被防火墙
  过滤 ICMP 的链路），就会出现"小包通、大包不通"。
  `net.ipv4.tcp_mtu_probing` 用**探测**的方式逐步试探可用 MTU 来绕过
  这个黑洞（代价是可能触发重传）。
- **ICMP 差错生成**：`icmp_send` → `__icmp_send`（`net/ipv4/icmp.c`），
  上层封装如 `icmp_unreach`（不可达）、`icmp_redirect`（重定向）、
  路由查找辅助 `icmp_route_lookup`。ICMP 有**速率限制**，避免成为放大攻击源。

### 3.5 RP filter（反向路径过滤）

开启 `rp_filter` 后，收到包时会用**源地址**反查路由，检查
"如果我要回给这个源，会不会走同一个接口进来"。检查函数是
`fib_validate_source` / `__fib_validate_source`
（`net/ipv4/fib_frontend.c`）。

| `rp_filter` 值 | 模式 | 行为 |
|---|---|---|
| 0 | 关闭 | 不检查 |
| 1 | **严格模式（strict）** | 反查得到的出口设备**必须**与入接口完全一致，否则丢弃 |
| 2 | **松散模式（loose）** | 只要求反查**能成功**（源地址在任何接口上可达即可），不要求接口一致 |

- 严格模式抗 IP 欺骗更强，但**多宿主 / 非对称路由**环境下会误杀。
- 松散模式容忍非对称路由，防护弱一些。
- 生产建议：用 `net.ipv4.conf.all.rp_filter` 与
  `net.ipv4.conf.<if>.rp_filter` 按接口细调，并注意
  `all` 与具体接口的取值是**取最大值**生效（这是常见困惑点）。

### 3.6 组播（IGMP）简要

组播不查普通单播 FIB，而是由组播路由（`ip mroute`）与 IGMP 共同处理。
主机侧的核心是 **IGMP**（`net/ipv4/igmp.c`）：`igmp_rcv` 处理收到的
IGMP 报文（Query/Report/Leave），`igmp_send_report` 发送成员报告，
`igmp_group_added` 在加入组时处理。注意 `ff00::/8` 之类的组播路由
在 `local` 表里以 `RTN_MULTICAST` 出现（见 §4 实测输出）。

## 4. 可观测点与验证方法

### 4.1 `/proc/net/fib_trie` —— 直接看 FIB trie 的形状

本机实测（节选）：

```
Main:
  +-- 0.0.0.0/0 3 0 4
     |-- 0.0.0.0
        /0 universe UNICAST
     +-- 10.0.0.0/24 2 0 1
        |-- 10.0.0.0
           /24 link UNICAST
        |-- 10.0.0.10
           /32 host LOCAL
        |-- 10.0.0.255
           /32 link BROADCAST
```

怎么读：`+-- <prefix>` 是**内部节点**（后面数字是 `key_vector` 的
`pos`/`bits` 等元数据）；缩进的 `|-- <ip>` 行是**叶子条目**，格式为
`/prefixlen scope TYPE`；`Main:`/`Local:` 对应不同 **FIB 表**（254/255）。
这与 §2.3 的 `key_vector` 注释完全对应：内部节点是 TNODE
（`(pos|bits) > 0`），叶子是 LEAF（`(pos|bits) == 0`）。

### 4.2 `/proc/net/fib_triestat` —— 结构与规模统计

本机实测：

```
Basic info: size of leaf: 48 bytes, size of tnode: 40 bytes.
Main:
	Aver depth:     2.38
	Max depth:      3
	Leaves:         13
	Prefixes:       13
	Internal nodes: 7
	  1: 3  2: 2  3: 2
	Pointers: 30
Null ptrs: 11
Total size: 2  kB
```

`size of leaf`/`size of tnode` 由 `LEAF_SIZE`/`TNODE_SIZE()` 宏给出
（`fib_triestat_seq_show`，`net/ipv4/fib_trie.c`）。`Max depth` 是查找的
最坏跳数 —— 只有 **3**，这正是"压缩前缀树很快"的直接证据。

### 4.3 `/proc/net/route` 与 `ip -j route`

`/proc/net/route` 是**十六进制、小端**的旧格式（`Destination` 和
`Gateway` 都是字节反序的 32 位值）：

```
Iface	Destination	Gateway 	Flags	RefCnt	Use	Metric	Mask		MTU	Window	IRTT
wlan0	00000000	011FA8C0	0003	0	0	600	00000000	0	0	0
docker0	000011AC	00000000	0001	0	0	0	0000FFFF	0	0	0
```

读法：`011FA8C0` 按字节倒过来是 `C0 A8 1F 01` = `10.0.0.1`。
`00000000` 目的地址 = 默认路由。**这就是很多人直接解析
`/proc/net/route` 时踩的坑** —— 它既不是点分十进制，也不是常规十六进制，
而是"内存里的原始字节"。建议改用 `ip -j route`（JSON、已解析）。

`ip -j route show`（本机实测，main 表）：

```
dst=default                via=10.0.0.1     dev=wlan0    table=main  proto=dhcp    type=unicast  metric=600 prefsrc=10.0.0.10
dst=172.17.0.0/16          via=-                dev=docker0   table=main  proto=kernel  type=unicast  prefsrc=172.17.0.1
dst=172.18.0.0/16          via=-                dev=br-...    table=main  proto=kernel  type=unicast  prefsrc=172.18.0.1
dst=10.0.0.0/24        via=-                dev=wlan0    table=main  proto=kernel  type=unicast  metric=600 prefsrc=10.0.0.10
```

`ip route show table all` 会额外显示 `local` 表，其中可见
`RTN_LOCAL`（本机地址 /32）、`RTN_BROADCAST`（广播地址）、
`RTN_MULTICAST`（如 `ff00::/8`）—— 即"路由类型"在用户态的体现。
`labs/03` 的 `./rtnl_dump route` 能看到全部 23 条（含 IPv6 与 local 表）。
`ip -s route` 会附加 `RTA_CACHEINFO` 统计（`used`/`age`）。

本机实测 `/proc/net/arp`：

## 6. 常见陷阱、调优旋钮、自测题

### 6.1 常见陷阱

1. **以为还有"路由缓存"**：4.18 起已移除 rtable cache，数据面直接查
   FIB trie。旧文档里的 `/proc/net/rt_cache` 已不存在。同一目的的两次
   查找不保证同一 `rtable` 指针。
2. **误把 `/proc/net/route` 当普通十六进制**：它是**小端字节序**的原始值，
   `011FA8C0` 要按字节倒读成 `10.0.0.1`。解析脚本极易出错，建议用
   `ip -j`。
3. **混淆 `local` 表与 `main` 表**：`ip route show` 默认只看 `main`；
   本机地址的 `RTN_LOCAL` 路由在 `local` 表。这解释了
   "为什么 127.0.0.1 不在 main 表里也能被本机接收"。
4. **`RTN_THROW` 与 `RTN_UNREACHABLE` 搞混**：`RTN_THROW` 表示
   "本表没找到确切匹配，去继续查**下一条策略规则/其他表**"，
   是策略路由里"回退"的机制；`RTN_UNREACHABLE` 是**直接失败**并回
   ICMP 不可达。
5. **`arp_ignore`/`arp_announce` 名字记错**：它们是 **sysctl**
   （定义在 `net/ipv4/devinet.c`），**不是函数**。源码里通过
   `IN_DEV_ARP_IGNORE(in_dev)` 这类宏读取。
7. **同一 netns 内用 veth 做 ARP 实验收不到应答**：veth 两端在同一
   网络命名空间时，对端地址是本机地址，内核发 ARP 应答时会走 `lo`。
   必须把两端放进**不同 netns**（`labs/04` README 有实测记录）。

### 6.2 调优旋钮

| 旋钮 | 作用 | 备注 |
|---|---|---|
| `net.ipv4.ip_forward` | 是否转发 | 默认 0 |
| `net.ipv4.conf.{all,<if>}.rp_filter` | 反向路径过滤 | 0/1/2；`all` 与接口取最大 |
| `net.ipv4.conf.{all,<if>}.arp_ignore` | 收到 ARP 请求时是否应答 | 0=任何本地地址都答；1=只有目标地址在本接口上才答（推荐多宿主） |

### 6.3 面试 / 自测题（≥8）

<details><summary>2. 本机地址是在哪里判定的？为什么会有 local 表？</summary>

内核在配置地址时（`fib_add_ifaddr`，`net/ipv4/fib_frontend.c`）会往
**local 表（表 id 255）** 插入该地址的 `/32` 路由，类型为 `RTN_LOCAL`；
同时插入广播地址的 `RTN_BROADCAST` 和网段的 `RTN_UNICAST` 到 main 表。
于是"目标是否本机"就变成了**一次普通的 FIB 查找**：
`ip_route_input_slow` 命中 `RTN_LOCAL` 后把 `dst->input` 设为
`ip_local_deliver`。这比遍历接口列表要高效、统一得多。
</details>

<details><summary>3. 为什么 4.18 删掉路由缓存？删了之后靠什么？</summary>

原因是可扩展性与一致性：全局共享的路由缓存在随机目的地址（如 DDoS）
下会剧烈颠簸，反而更慢；且路由/接口变更时需逐条失效，易漏。
删除后数据面**直接查 FIB LC-trie**（`fib_table_lookup`），
查找约 O(W) 且各 CPU 可并行。真正需要缓存的部分被拆到
邻居子系统（ARP 结果）和 fnhe（PMTU/redirect 例外）。
可用 `/proc/net/fib_triestat` 的 `Max depth` 佐证 trie 很浅（本机为 3）。
</details>

<details><summary>4. `rtable` 与 `dst_entry` 什么关系？`skb->dst` 有什么用？</summary>

`struct rtable` 的**第一个成员**就是 `struct dst_entry dst`，
所以两者可以互相强转；`dst_entry` 是"下一步怎么走"的通用抽象
（含 `input`/`output` 函数指针、`dev`、`ops`、metrics），
`rtable` 是它在 IPv4 的具体化。`skb->dst` 随包携带这次查找的结果，
避免同一个包反复查 FIB，并让分片、邻居解析、PMTU 等下游代码能拿到
出口设备与 MTU。
</details>

<details><summary>6. ARP 解析期间，待发的包去哪了？NUD 状态怎么变？</summary>

`neigh_output` 发现邻居不是 `NUD_CONNECTED` 时转到
`neigh_resolve_output`，后者调用 `__neigh_event_send`：
若状态是 `NUD_INCOMPLETE` 或需要新建，则把 skb 挂到
`neighbour` 的 `arp_queue` 上**排队**，同时发送 ARP 请求；
收到应答后 `arp_process` → `neigh_update` 更新为 `NUD_REACHABLE`
并冲刷队列把包发出。若探测次数用尽则变 `NUD_FAILED`，包被丢弃。
注意 `NUD_STALE` **不会**排队，仍可直接发包。
</details>

<details><summary>7. netfilter 的 5 个 hook 分别在哪？</summary>

PRE_ROUTING（`ip_rcv` 后、路由前）、LOCAL_IN（判定本地后、进传输层前）、
FORWARD（判定转发后）、LOCAL_OUT（本机发包、路由前）、
POST_ROUTING（路由后、真正发出前）。统一由 `NF_HOOK` 宏调用，
返回 `NF_ACCEPT` 时继续执行 `okfn`。
</details>

<details><summary>8. rp_filter 的严格模式与松散模式区别？</summary>

严格(1)：用源地址反查得到的**出口设备必须等于入接口**，否则丢包，
能有效防源地址欺骗，但非对称路由会误杀。
松散(2)：只要求反查**能成功**（源地址在任何接口上可达），不比对接口，
容忍非对称路由但防护较弱。检查函数是 `fib_validate_source`。
</details>

<details><summary>9. PMTU 是怎么发现和记录的？PMTU 黑洞怎么办？</summary>

带 `DF` 的包过大时，中间路由器回 ICMP Fragmentation Needed，
本机在 `ip_rt_update_pmtu`（`net/ipv4/route.c`）中更新路径 MTU，
结果记录在下一跳的 fnhe（`fib_nh_common.nhc_exceptions`）。
若中间设备静默丢包不回 ICMP，就会"小包通、大包不通"，
即 PMTU 黑洞；可用 `net.ipv4.tcp_mtu_probing` 主动探测绕过。
</details>

<details><summary>11. IPv6 的邻居发现和 ARP 有何对应关系？</summary>

IPv6 用 **NDP（Neighbor Discovery Protocol）** 取代 ARP：
接收处理入口是 `ndisc_rcv`（`net/ipv6/ndisc.c`），发送请求/通告是
`ndisc_solicit`、`ndisc_send_na`（Neighbor Advertisement）。
它复用**同一套邻居子系统**（`struct neigh_table` / `struct neighbour` /
NUD 状态机），因此 `ip neigh` 能同时显示 v4 与 v6 邻居。
IPv6 还多出路由器发现（RS/RA）与地址自动配置，这是 ARP 没有的。
IPv6 的路由子系统在 `net/ipv6/route.c`（`ip6_route_input`、
`ip6_route_output_flags`、`ip6_pol_route`），与 IPv4 的 FIB 是**两套
独立实现**（不是共用 fib_table）。
</details>

## 7. 本章小结 + 延伸阅读

### 小结

- **网络层做三件事**：路由决策、策略校验、投递（本地/转发/发出）。
- **FIB 是三层结构**：`fib_table`（表）→ trie 节点
  （`key_vector`/`tnode`）→ `fib_alias`（条目）→ 共享的
  `fib_info` + `fib_nh`/`fib_nh_common`（下一跳）。
- **4.18 是关键分水岭**：路由缓存被删除，数据面直接查 LC-trie；
  不要再用旧模型的直觉理解现代内核。
- **`dst_entry` 是"下一步"的抽象**，`rtable` 把它具体化为 IPv4 路由，
  通过首成员嵌入实现无开销强转；`skb->dst` 让结果随包走。
